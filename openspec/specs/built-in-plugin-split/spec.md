# built-in-plugin-split Specification

## Purpose
Keep DataFiles and image responsibilities in non-public helpers while preserving built-in plugin ownership, parsing safety, serialized outputs, native calibration and caller-owned logging contracts.

The independent extraction's 426-type/19-assembly proof, move-only source boundary and item 1 isolation are historical, retained in its archived artifacts. The approved joint state instead composes with `notion-compatibility-migration` and `notion-relation-fallback-diagnostics` at 425 types / 18 assemblies; that Notion migration owns the approved CLR break. Current resize cleanup is governed by the separately accepted `image-resize-temp-cleanup` repair, not by retention of the inherited extraction-time bug.

## Requirements

### Requirement: Internal responsibility extraction preserves plugin ownership

The migration SHALL retain the two existing internal plugin entries, identities, interfaces, registration order, namespace, and Engine assembly. The eleven responsibility types in ten helper files and supporting wrappers/contexts MUST remain non-public and MUST NOT own plugin registration.

#### Scenario: Discover built-in implementations after extraction
- **WHEN** the registry and architecture guards inspect the migrated assembly
- **THEN** the original entries remain the sole plugins for these responsibilities and all extracted types are internal implementation details
- **AND** the split SHALL add no public helper surface and SHALL preserve the accepted joint public baseline byte-identically at 425 types / 18 assemblies, without reversing the separately approved Notion CLR break.

### Requirement: DataFiles retains parsing and safety contracts

The migration MUST preserve constructor validation/defaults/error details, the private opener seam, no-follow and verified stream ownership, strict decoding, cancellation, deterministic traversal, all ten limits and exception/disposal behavior. Projection MUST retain typed keys, graph/scalar types, comparers, order, YAML alias copies and first-document projection with validation of later documents.

#### Scenario: Reuse a plugin for mixed language/default inputs
- **WHEN** JSON and multi-document YAML with an alias are loaded across a configured language and default data
- **THEN** byte and projection budgets are shared across those inputs within one call
- **AND** the next call receives fresh budgets and produces the same exact graph consumed by templates and canonical hashing.

### Requirement: Images retain serialized, native, ownership and logger contracts

The migration MUST preserve execution/early-return order, cancellation, native validation and calibration, quality/dimensions, freshness compact UTF-8 bytes and property order, source/variant identities, HTML rewrite behavior, user-file protection, tracking tuples and atomic publication/sidecar order. Unchanged cleanup nesting was the original extraction boundary; current invocation-owned cleanup MUST follow `image-resize-temp-cleanup`. Caller-owned ILogger MUST remain required through discovery and both external runner calls; no replacement/default logger is permitted.

#### Scenario: External resize succeeds
- **WHEN** the public plugin entry generates representative original-format variants
- **THEN** the exact freshness bytes, normalized srcset graph/order, and variant-plus-sidecar tracking tuples match the baseline contract.

#### Scenario: External resize exits nonzero
- **WHEN** a counted caller logger wraps a JSON Warn or Error sink
- **THEN** the original warning payload is counted once before filtering, never bypasses the sink through stdout, and no failed output is published or tracked.

#### Scenario: Inherited resize cleanup boundary
- **WHEN** the original extraction encountered external execution throwing before its cleanup try/finally
- **THEN** that historical extraction retained the inherited boundary and recorded `I-IMAGE-TEMP` rather than claiming complete temporary-file cleanup.
- **AND** the separately accepted `image-resize-temp-cleanup` contract SHALL govern current backend execution and cleanup; this historical scenario MUST NOT require retaining the repaired bug.

### Requirement: Verification remains scoped and reproducible

For the original extraction, the writer MUST use the exact controller-scheduled complete specialties and direct API check described in its archived `2026-10-26-migrate-built-in-plugin-split/design.md` and external commands handoff; assertion RED MUST precede production extraction. That task-scoped acceptance is historical and does not prohibit the separately approved isolated joint integration. GREEN evidence MUST fingerprint current HEAD, affected/build/read/fixture inputs and dynamic membership, exact commands, environment states only, and SDK/toolchain, with official cache record/check.

#### Scenario: Complete migration handoff
- **WHEN** the writer finishes the original approved independent extraction
- **THEN** full scoped logs/TRX/API/cache evidence and self-review are handed to the parent in review_wait
- **AND** that historical handoff remains isolated from item 1 work and contains no commits/publication, excluded partial integration tests, historical replay, or full/release/whole-solution/aggregate gates; the separately approved current joint integration is not part of that historical isolation restriction.
