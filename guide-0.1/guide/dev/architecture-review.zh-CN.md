# 项目架构评审意见稿（P1 对齐版）

本文档从维护者视角，对当前仓库架构做一次偏正式评审。目标不是重复模块说明，而是回答三件事：

- 当前架构是否总体合理
- 哪些设计应继续保留
- 哪些风险需要优先治理

## 1. 评审结论

当前仓库（以 `bukit.slnx` 与 `src/Bukit.*` 为边界）的整体架构依然是成熟且可维护的工程化架构，主要优点：

- 分层清晰，主链路稳定
- 单向依赖健康
- 插件扩展边界明确
- 测试矩阵可运行，覆盖核心路径

同时，现阶段的主要风险已从“核心代码失效”转为“能力边界与治理一致性”：

- 超大规模站点下的正文读取/缓存策略仍需基准化治理
- 路由/模板需求已进入配置驱动模型，需要防止固定角色回流核心
- CLI 轻量实现在命令规模增长后有维护上限
- 文档与交付资产的一致性需要持续机制而非一次修复

## 2. 评审范围

本次评审覆盖：

- Bukit 主体：CLI、Config、Content、Routing、Rendering、Engine、Plugins
- 构建模式：普通 .NET 模式与 Native AOT 模式
- 文档与交付治理：架构结论与仓库现实的一致性

本次不聚焦具体业务功能正确性，而聚焦：

- 结构合理性
- 可维护性
- 可扩展性
- 可测试性
- 治理一致性

## 3. 主要优点

### 3.1 模块职责边界清楚

当前主链条清晰：

```text
CLI -> Config -> Content -> Routing -> Rendering -> Engine -> Plugins -> Output
```

各层职责克制且可定位，维护成本可控。

### 3.2 单向依赖设计合理

当前没有明显“底层反向依赖上层”的迹象：

- CLI 依赖 Engine / Config
- Engine 依赖 Content / Routing / Rendering
- Plugins 通过 Abstractions 契约访问系统

### 3.3 插件体系抽象正确

插件扩展点分为：

- `derive-pages`
- `after-build`

该划分贴合静态站点生成器的领域模型，便于治理执行顺序、失败策略与产物边界。

### 3.4 内容正文模型已明显改进

当前主链已不是“正文 HTML 一定提前常驻内存”的形态。`ContentDocument` 支持 `BodyKey`，正文可经 `IContentBodyStore` 按需获取；Markdown/Notion provider 默认可返回 `ContentHtml: null` 并延迟解析。

这意味着正文模型已从“全量正文常驻”演进到“元数据全量 + 正文按需”。

## 4. 主要不足与局限

### 4.1 大规模场景的正文读取与缓存策略仍需基准化

#### 现状

正文加载机制已延迟化，但渲染、搜索、RSS、分页等阶段仍会在不同路径触发正文读取；在超大规模内容集下，读放大与峰值行为仍需量化。

#### 风险等级

- **中高**

#### 影响范围

- 万级以上内容站点
- 多语言构建
- CI 资源受限环境

#### 建议方向

- 为正文读取建立阶段性基准（读取次数、峰值内存、耗时分布）
- 结合增量 manifest 明确“可跳过读取”的判定规则
- 对高频消费路径（search/rss/list）制定统一缓存策略

### 4.2 路由与模板需求必须保持配置驱动

#### 现状

系统通过 `collections`、显式 route/template 与主题 `templates.accepts` 驱动路由与模板选择；核心不应维护 `post/page` 默认规则或固定模板路径。

#### 风险等级

- **中**

#### 影响范围

- 新增内容类型时的一致性
- 主题与 doctor 模板需求校验的长期可预测性

#### 建议方向

- 在文档、示例和 starter 中统一使用显式 collections / template 规则
- 为“无匹配模板失败”“required 模板检查”“home 默认 pages/index.html”补齐契约性测试样例

### 4.3 CLI 层扩展性有限

#### 现状

CLI 采用轻量参数解析实现，优势是可控、AOT 友好、依赖少；但命令持续扩展后，声明式能力与统一错误体验不足。

#### 风险等级

- **中**

#### 建议方向

- 保留轻量实现
- 增加统一命令元数据层（参数定义、校验、help 生成、错误文案）

### 4.4 AOT 对动态插件生态存在天然收缩

#### 现状

- 非 AOT：支持外部程序集插件
- AOT：动态扩展应优先走 external-protocol / process（wasm 需按约束使用）

#### 风险等级

- **中高**

#### 建议方向

- 明确双模式定位并固化文档口径
- 持续增强进程外协议插件治理（能力声明、失败语义、安全边界）

## 5. 额外值得关注的结构性问题

### 5.1 Notion 侧复杂度持续集中

字段解析、块渲染、relation、taxonomy、缓存、限流能力都在内容层汇集，仍需坚持组件化边界（解析器/渲染器/API 适配/缓存策略分离）。

### 5.2 文档与仓库资产一致性需要机制化

过去已出现“文档声明存在但仓库资产缺失”的情况（如 workflow、历史模块路径）。这类问题会直接降低维护者定位效率。

建议：

- 对关键文档做路径可达性检查（solution、目录、workflow）
- 把“仓库边界”写入入口文档并作为变更守则

### 5.3 发布路径需要单一事实来源

应保持发布路径描述唯一、可执行、可验证，避免多个文档各自表达导致维护者误判。

## 6. 综合评分（当前口径）

| 维度 | 评分 | 说明 |
|---|---|---|
| 可维护性 | 8.6 / 10 | 分层与边界清晰，主线可定位 |
| 可扩展性 | 8.1 / 10 | 插件与模块抽象合理，配置驱动边界需持续治理 |
| 可测试性 | 7.6 / 10 | 核心测试矩阵稳定可运行 |
| 可交付性 | 7.4 / 10 | 主线可交付，但文档与资产一致性需持续治理 |
| 规模化潜力 | 7.2 / 10 | 正文模型已改进，超大规模基准仍待补齐 |
| 开放生态潜力 | 6.8 / 10 | AOT 边界客观存在，协议扩展路径需继续强化 |

## 7. 优先级建议

### 优先级 1：补齐“正文读取与缓存”基准治理

目标：

- 量化读取行为与峰值资源
- 形成可回归的性能基线

### 优先级 2：巩固配置驱动路由与模板需求治理

目标：

- 保持 collections、显式 template/route、主题 accepts 作为唯一扩展路径
- 防止未来扩展时重新引入固定角色与默认页面路径

### 优先级 3：建立文档-资产一致性检查

目标：

- 防止路径/工作流/模块失真再次累积
- 让文档继续成为可执行入口，而非历史快照

## 8. 最终判断

这不是一个“架构混乱”的项目。  
更准确地说，它是一个主链成熟、边界清晰、工程纪律较好的静态站点引擎仓库；当前主要挑战不在于重写核心代码，而在于把“规模化治理”和“文档一致性治理”持续机制化。
