# 构建耗时与增量构建：逐问题修复方案与实施细则

- 状态：**已完成**（2026-11-11）。阶段 0a–6 全部实施并验收：阶段 1、2、3、6 随 v2.0.13 发布，阶段 5 随 v2.0.14 发布，阶段 4 在站点仓库完成；问题 4 的诊断警告（`stabilize-render-dependency-inputs`）在 Unreleased。已发布的七份变更已归档到 `openspec/changes/archive/2026-11-11-*`。逐问题的验收数据见汇总文档。

- 日期：2026-11-10

## 0. 先读这一段

1. **真正能把 29 分钟降下来的是问题 1（渲染重复转换）。** 其余问题要么是正确性，要么只在“内容完全没变”的构建里才省时间。
2. **增量构建在日常使用中短期内帮不上忙。** 即使修好签名链接，`site.data.pages_by_id`（`PagesIndexPlugin` 写入的全站页面数据）仍在全站依赖哈希里，任意一篇文章改动都会让全站重渲染。这一点 11-08 的计划已经记录，汇总文档没有提。要让“改一篇只渲染一篇”成立，需要问题 5 的按页面依赖，属于设计级变更。
3. **汇总文档对 4352 页的归因可能不准。** 文档只怀疑 `modules`；从代码看 `pages_by_id` 是更直接的嫌疑：它包含每一页的自定义字段；字段值无论是原始签名链接还是随签名变化的本地化文件名，都会让全站哈希每次不同。阶段 0 的验证要同时覆盖两者。
4. **`site` 对象的转换同样随页数增长**（它带着 `pages_by_id`）。所以列表页的 3 分钟确实与文章页同因，问题 1 的修复对列表页也有效。这修正了我上一轮写进文档的“占比未测”建议的前半句。
5. **问题 1 之后，报告阶段会变成最大的一块。** 约 5 分钟的“审查和报告”在提速后的构建里约占一半，而且增量构建跳不过它。所以问题 11 紧跟问题 1 处理。
6. **计划值不值得做，取决于两项还没有的数据**：转换在渲染耗时里的占比（V3），以及文章模板是否遍历 `pages`（V6）。这两项是阶段 0 的第一批，结果出来之前不启动任何 Core 改动。

### 预期收益（估算，非实测）

按汇总文档的数据推算：本地 21 分钟中渲染约 14 分钟、报告约 5 分钟、其他约 2 分钟；CI 约为本地的 1.4 倍。

| 情形 | 本地 | CI |
|---|---|---|
| 现在 | 约 21 分钟 | 约 29 分钟 |
| 只做问题 1，转换占渲染八成以上 | 约 9 到 10 分钟 | 约 13 到 14 分钟 |
| 只做问题 1，转换只占一半 | 约 14 分钟 | 约 19 到 20 分钟 |
| 再做完增量各项，且内容无改动 | 约 7 分钟 | 约 10 分钟 |

报告阶段若能优化，以上各行还能再减，上限 5 分钟（本地）。

## 4. 阶段 0：验证与基线（不改 Core）

所有实验用同一台机器、同一份缓存、同一个 Bukit 二进制，并记录二进制的版本串。

### V1 依赖哈希为什么每次都变

- **做法**：在站点仓库临时加一个不提交的诊断模板，把 `site.modules`、`site.data`（重点是 `pages_by_id` 的 `fields`）、`site.data_index`、`related_pages` 输出为 JSON 文件；间隔 1 小时以上构建两次，对两份 JSON 做差异比较。
- **判定**：差异落在哪个键，哪个键就是来源。同时记录差异值的形态：原始签名链接，还是本地化后的文件名。
- **影响**：决定问题 4 的修法是“靠问题 7 自动解决”还是“还需要让未本地化的字段进入本地化”。

### V2 295 页的元数据为什么变

- **做法**：同一份 JSON 里按页比较 `fields`；同时比较两次构建后媒体下载目录的文件名清单。
- **判定**：变化的字段名、字段类型（封面、文件属性等）和页数是否等于 295。

### V3 转换耗时的构成

- **做法**（任选其一，都不需要提交代码）：
  1. 用 JIT 版本（`dotnet run -c Release`）配合 `dotnet-trace` 采集分配与 CPU 采样，按调用栈看 `ScribanPageModelMapper`、`ScribanSiteModelMapper`、`ScribanDynamicValueMapper` 各占多少。
  2. 对照实验：临时关闭 `PagesIndexPlugin` 构建一次，看 `variantTotal` 下降多少，得到 `site.data.pages_by_id` 这部分的上限。
- **判定**：`pages` 转换、`site` 转换、模板执行、HTML 变换、写文件各自的占比。若转换合计低于一半，问题 1 的预期收益要下调，并回到采样结果找真正的热点。

### V4 服务器 GC 是否生效

- **做法**：用命令行属性发布一个对照二进制（`-p:ServerGarbageCollector=true`，不改项目文件），与现有二进制同条件各跑一次；记录耗时、CPU 核数利用和峰值内存。
- **判定**：若对照二进制明显更快，说明此前的环境变量没有生效，问题 3 有独立收益；若没有差别，按“分配量本身是瓶颈”处理，等问题 1 之后再测。

### V5 报告阶段的 5 分钟（第一批）

- **做法**：阶段 0 只能粗测。用采样工具在报告阶段采 2 到 3 次调用栈，记下最常出现的写入器；同时记录报告阶段的起止时间，确认“约 5 分钟”这个数。精确拆分放到问题 11。
- **影响**：若某一个写入器明显占主导，问题 11 的优化方向可以提前确定，分项计时与优化合并为一个变更。

### V6 文章模板是否遍历 `pages`（第一批）

- **背景**：两份文件说法相反。汇总文档说 silkroutecc 的文章模板不使用 `pages`；`harden-incremental-invalidation` 提案说站点的 `related-entity.html` 被文章页和公司页引用，并遍历 `pages`。
- **做法**：在站点仓库的主题里搜索文章页模板及其引用的所有局部模板，列出对 `pages`、`site.data.pages_by_id` 的每一处遍历或查找。
- **判定与影响**：
  - 不遍历：问题 1 能省掉全部转换成本，按预期收益表的第二行估计。
  - 遍历：每篇文章还要在模板里循环一遍全站索引，这部分问题 1 省不掉。需要估算循环成本，并考虑在主题侧改为按键查找（站点任务），或把问题 1 的 Non-Goals（按需转换）提前。
  - 无论哪种结果，都要把汇总文档和提案里不一致的那一处改正。

### 基线记录

每次实验记录：总耗时、`variantTotal`、`renderDependencyHash`、峰值内存、CPU 利用、`renderReasons` 各原因的页数。文件放在仓库外，结论写回汇总文档。

## 5. 逐问题方案

### 问题 1：每页重复转换 `pages` 和 `site`

**根因。** `ScribanRootModelMapper.ToScriptObject(PageModel)` 每渲染一页都执行两件事：
- `ScribanListModelMapper.ToPageInfoScriptArray(model.Pages)`：把全站约 4650 条页面索引逐条转换，并展开 `fields`、`content_model`、`entities`、`seo` 等子对象。
- `ScribanSiteModelMapper.ToScriptObject(model.Site)`：转换 `params`、`modules`、`data`（含 `pages_by_id`）、`data_index`。

两者都随页数增长，所以总成本随页数平方增长。列表页走另一条路径，但同样每页转换一次 `site`。

**方案。** 按 `fix-render-shared-model-cost` 实施，并建议对提案做四处补充：

| 补充 | 理由 |
|---|---|
| 明确写出 `site` 转换也随页数增长，列表页同样受益 | 现提案只把 `site` 当作附带项 |
| 列表页的 `pages` 与 `items` 指向同一来源时只转换一次，两个名字共用同一个只读数组 | 现在同一份列表数据转换两遍；共用后输出不变 |
| `staticRender` 的计时也改为实际值 | 第 289 行同样写死为 0，提案漏了 |
| 删除“瓶颈不是回收策略”的断言，改为待 V4 验证 | 现有证据不足 |

**实施步骤。**

1. **基线**：完成 V3，保存改动前的输出目录作为逐字节对比的参照。
2. **共享缓存**（`ScribanTemplateRenderer`）：
   - 新增一个内部持有者，保存“最近一次的 `pages` 来源引用及其转换结果”和“最近一次的 `SiteModel` 引用及其转换结果”，用引用相等判断命中。
   - 并发下用延迟初始化保证每个来源只转换一次；来源引用变化时整体替换，不累积旧批次。
   - 渲染器现有的公共方法签名不变。
3. **映射改造**（`ScribanRootModelMapper`）：
   - `PageModel` 路径从持有者取 `pages` 和 `site`；`page`、`seo` 等每页不同的值仍每页新建。
   - `ListPageModel` 路径只共享 `site`；`pages`、`items` 仍按列表各自转换，但同源时只转换一次。
   - `ScribanDerivedListAliasProjector` 只改根对象上的别名，不触碰共享值，行为保持。
4. **冻结**：写一个递归冻结函数，把共享的数组、对象及全部嵌套值设为只读。在 Scriban 7.2.5 上先用测试确认两件事：只读对象被模板写入时报错；只读对象被多个线程同时读取是安全的。
5. **排查写入方**：搜索内置主题、示例主题、测试夹具和 `ITemplateContextContributor` 的实现，确认没有任何一处写入 `pages` 或 `site` 的成员。有的话先改写入方或把该成员排除出共享。
6. **计时**（问题 2 的一部分，见下）。
7. **测试**（按提案 tasks 第 4 节），重点三项：
   - 同一批次内两次渲染拿到的是同一个 `pages`、`site` 实例；
   - 并发渲染结果与串行逐字节一致；
   - 代表性夹具改动前后输出目录逐字节一致。
8. **现场验证**：silkroutecc 同条件构建，比较 `variantTotal`、`pageRender` 合计、总耗时、峰值内存；用目录比较工具确认输出与改动前一致。

**涉及文件。** `Bukit.Rendering/Scriban/` 下的 `ScribanTemplateRenderer.cs`、`ScribanRootModelMapper.cs`、`ScribanListModelMapper.cs`、`ScribanSiteModelMapper.cs`、`ScribanDynamicValueMapper.cs`；`Bukit.Engine/PageRenderDispatcher.cs`。

**验收标准。**
- 输出逐字节不变；公共 API 基线不变。
- silkroutecc 的 `variantTotal` 显著下降。不预先承诺数值；若降幅低于 V3 测出的转换占比，视为未达预期，需要解释差距。
- 峰值内存不高于改动前。

**风险与回退。**
- 第三方主题若写入 `site` 或 `pages` 的嵌套值，升级后会报只读错误。CHANGELOG 要写明；回退方式是撤销该发布，不提供开关。
- 共享对象被并发读取若在 Scriban 内部触发写入（例如惰性成员），会出现偶发错误。步骤 4 的并发测试是这项风险的门槛，不通过就不能合并。

### 问题 2：渲染计时写死为 0

**根因。** `PageRenderDispatcher` 中 `pageRender`、`listBuild`、`staticRender` 三处 `AddDuration(..., 0)`。`SpecialListRenderer` 里的 `listBuild` 是真实计时。

**方案与步骤。**
1. 三处改为从组装页面模型到写出文件的实际耗时。
2. 建议同时增加三个细分计时：模型转换、模板执行与 HTML 变换、写文件。这是新增指标名，`metrics.json` 的结构不变；是否加入需要你确认，因为它扩大了问题 1 提案的范围。
3. 测试：三项计时大于 0；并发下累计值不丢失。

**验收标准。** `variantTotal` 与各细分计时之和的差距小于 10%，不再有 890 秒无指标的情况。

### 问题 3：10 个线程只用约 2 个核

**根因（未定）。** 两种解释都与现象相符：分配量过大导致频繁回收，而工作站 GC 回收时暂停全部线程；或者存在未发现的串行点。渲染路径上没有找到全局锁，只有按文件的写锁。

**方案。** 不单独立项，按数据决策：

| V4 与问题 1 之后的结果 | 动作 |
|---|---|
| 问题 1 之后 CPU 利用恢复到多核 | 结束，不动 GC 设置 |
| 仍只用约 2 个核，且 V4 显示服务器 GC 明显更快 | 新变更：在 CLI 发布配置中启用服务器 GC；先在 4 核 CI 机器上测峰值内存 |
| 仍只用约 2 个核，服务器 GC 无帮助 | 用问题 2 的细分计时和采样找串行点，再定方案 |

**风险。** 服务器 GC 会提高内存占用；CI 机器内存有限，启用前必须有峰值内存数据。

### 问题 4：全站依赖哈希每次都变

**根因。** `SiteModelDataContributor` 把 `site.modules` 的内容和字段、`site.data` 的全部公开键、`data_index`、`related_pages` 逐节点写入全站依赖哈希。其中只要有一个值每次构建都不同，全站都被判为 `render_dependency_changed`。两个嫌疑：
- `site.data.pages_by_id`：`PagesIndexPlugin` 把每个已路由页面的自定义字段原样放进去；对通过关联解析出来的外部页面，它用自己的下载器本地化图片字段，文件名是完整链接的哈希，签名一变文件名就变。
- `site.modules` 的字段：`fieldPolicy: all` 下可能带原始签名链接。

**方案。** 分三层，前一层解决不了才做后一层：

1. **靠问题 7 自动稳定**：图片缓存键去掉签名后，本地化文件名不再变化。若 V1 显示差异全部是本地化文件名，问题 4 到此解决，不需要新代码。
2. **让残留的签名链接进入本地化**：若 V1 显示有原始签名链接留在模型里（模块字段、非图片文件属性、下载失败后保留的链接），扩大本地化覆盖面，使它们变成稳定的本地路径。
3. **诊断提示**：增量开启时，若模型里仍有已识别签名方案的链接，输出一条汇总警告，说明这些页面每次都会重渲染以及涉及的数据键。

**明确不做：在哈希里忽略签名参数。** 这样做会让页面被跳过，而输出目录里的旧 HTML 仍带着已过期的签名链接，结果是线上图片或文件 403。链接会过期的内容必须每次重渲染，或者先本地化。

**实施步骤。**
1. 完成 V1，把结果写入新变更 `stabilize-render-dependency-inputs` 的 proposal。
2. 若只需第 1 层：该变更只包含第 3 层的诊断提示和一个回归测试（同一输入连续两次构建，全站依赖哈希相同）。
3. 若需第 2 层：先确认模块字段和页面字段当前走的是哪条本地化路径，再定改动点；`PagesIndexPlugin` 自建的下载器要与主下载器共用同一身份函数（问题 7 的提案已要求）。
4. 测试：带签名链接的模块字段两次构建哈希相同；本地化关闭时出现诊断警告且页面照常重渲染。

**涉及文件。** `Bukit.Engine/Incremental/SiteModelDataContributor.cs`（只加诊断，不改哈希内容）、`Bukit.Engine/Plugins/BuiltIn/PagesIndexPlugin.cs`、`Bukit.Content/Media/`。

**验收标准。** silkroutecc 在内容无改动、间隔超过 1 小时的两次 `--no-clean` 构建中，`render_dependency_changed` 为 0。

### 问题 5：任意文章改动导致全站重渲染

**根因。** 全站只有一个依赖哈希，而 `pages_by_id` 和分类数据包含每篇文章的标题、摘要、字段。改一篇文章就改变全站哈希。

**方案。** 沿用 11-08 计划的方向，新建 `add-per-page-render-dependencies`。与问题 1 提案的 Non-Goals（按需转换与读取记录）合并设计：

1. 渲染时记录每个路由实际读取了哪些共享数据集合（`pages`、`pages_by_id`、分类、模块等）。
2. 全站哈希拆成“配置与主题”部分和若干“数据集合”部分；页面只叠加自己读取过的集合的指纹。
3. 读取记录缺失、模板或引擎变化时，退回现在的全站哈希。

**前置条件。** 问题 1、4、8 完成，并且有问题 2 的指标可以量化收益。在此之前不排期。

**文档口径。** 在这项完成之前，对外说明应写成：`--no-clean` 只在内容没有任何改动的构建中跳过页面。

### 问题 6：295 页每次 `content_changed`

**根因。** 按 `PageRenderDispatcher` 的判定顺序，在全站依赖哈希已变的情况下，`content_changed` 只能来自元数据哈希（页面记录加自定义字段）变化，不是正文变化。最可能的来源是页面字段里的签名链接或随签名变化的本地化文件名。正文是否变化被上一条原因盖住，目前不可见。

**方案与步骤。**
1. V2 确认变化的字段。
2. 随问题 7 和问题 4 的第 2 层解决，不单独立项。
3. 建议把元数据变化的原因名从 `content_changed` 改为独立的名字，使报告能区分元数据变化与正文变化。这会改变报告里的原因取值，需要同步测试和文档；是否做需要你确认。

**验收标准。** 与问题 4 相同的两次构建中，`content_changed` 为 0；之后再看正文层面是否还有残留。

### 问题 7：图片缓存键含签名参数

**方案。** 按 `fix-media-signed-url-identity` 的 tasks 实施，不重复列出。补充三点：

1. 提案和 tasks 中的“随 v2.0.12 发布”改为“随下一版本发布”，版本号在发布时确认。
2. 该提案改写了一个 Core 定义性测试（`SamePathDifferentQuery…`），任务书里要单独标出并在审查时重点看。
3. 现有媒体缓存里约 565 个历史文件不会被自动清理，升级后手动清理一次，或等孤儿回收的变更。

**验收标准。** 站点上间隔超过 1 小时连续构建两次，第二次媒体下载数为 0，下载目录无新增文件。

### 问题 8：引擎版本、插件选项不参与失效

**方案。** 按 `harden-incremental-invalidation` 的 tasks 实施。补充三点：

1. **先验证版本串**：提案引用的先例读的是 SkiaSharp 程序集的版本，不能证明 `Bukit.Engine` 的版本串里带提交号。实施第一步是在 AOT 二进制里实际读出该值并确认形如 `版本号+提交号`；若发布流水线没有写入提交号，要先补上，否则同版本号的修复无法触发失效。
2. **插件选项里的密钥**：选项整体进入哈希，密钥轮换会触发全站重渲染。确认哈希写入器不会把原值写进日志或报告。
3. **必须先于阶段 4**：站点改用 `--no-clean` 之前，这项必须已发布，否则升级 Bukit 后会留下旧页面。

**验收标准。** 同一夹具连续两次 `--no-clean` 全部命中；更换引擎身份后页面、列表、特殊列表全部重渲染；改一个插件选项后全部重渲染。

### 问题 9、10：Notion 正文缓存契约与分钟精度

**方案。** 按 `fix-notion-body-cache-contract` 的 tasks 实施。补充两点：

1. **单独发布**：升级后首次构建会重拉约 3500 篇正文，多约 20 分钟。发布说明要写明，并提前确认 CI 超时（现为 120 分钟）足够。
2. **公共 API**：`NotionClient.SendAsync` 在公共 API 基线内，传递响应时间只能用内部成员；实施后跑一次 API 漂移检查确认基线不变。

**验收标准。** 契约版本递增后未编辑的文章被重新渲染；同一分钟内先抓取后编辑的内容在下一次构建生效。

### 问题 11：“审查和报告”约 5 分钟

**根因（未知）。** 报告阶段由 8 个写入器加 SEO 诊断组成，没有分项计时。

**排期。** 紧跟问题 1：分项计时与问题 1 放在同一个发布里，这样一次现场构建就能同时得到渲染和报告两部分的新数据；优化放在阶段 2。增量构建跳不过报告阶段，所以这里省下的时间每次构建都有效。

**方案。**
1. 新变更 `observe-report-stage-timing`：给每个报告写入器、SEO 诊断、构建后插件各加一项计时。只加指标，不改行为。
2. 用新指标在 silkroutecc 上测一次，按占比排序。
3. 针对前两名再定优化。常见的候选是对全部输出文件逐个计算校验和，以及重新读取已写出的 HTML；可行的手段是并行计算、复用渲染时已有的内容哈希、或让非发布构建跳过发布专用报告。这些只是候选，没有数据前不动手。

**验收标准。** 报告阶段各项计时之和与阶段总耗时的差距小于 10%。

### 问题 12：站点 CI 每次清空输出目录

属于站点仓库任务，在问题 7、8 发布且问题 4 验收之后进行。

**步骤。**
1. 站点配置去掉 `build.clean: true`，CI 构建命令使用 `--no-clean`。
2. CI 缓存三样东西：输出目录、缓存目录中的 `build-manifest.json`、媒体下载目录。三者恢复到与上次相同的绝对路径；清单绑定输出目录的绝对路径，路径变了会全量渲染。
3. 缓存键每次构建保存一份新的，恢复时取最近一份。
4. 每周一次或手动触发的 `--clean` 构建，兜住已知局限：引用 `pages` 的主题在增量下可能显示其他文章的过期标题。
5. 升级 Bukit 版本的那次构建不需要手动清理，问题 8 会让它全量渲染。
6. 上线前确认一件事：`--no-clean` 下被删除页面的旧输出文件会被清掉。

**验收标准。** 内容无改动的 CI 构建中，页面全部为 `unchanged`，渲染阶段耗时降到分钟以内；发布产物与一次 `--clean` 构建逐字节一致。
