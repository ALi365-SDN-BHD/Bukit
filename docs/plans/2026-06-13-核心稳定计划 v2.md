Bukit Core / Labs 边界收尾执行计划 v2
0. 总原则

历史文档状态标注（2026-07-05）：本文是历史执行计划，保留当时的迁移路径和旧机制名词。文中的 `experimental/Bukit.Labs.Protocol`、`site.externalPlugins`、`ExternalProtocolPluginSource`、`ProtocolEchoPlugin` 或 sample plugin 描述不代表当前实现；当前正式外部插件路径为 `Bukit.PluginHost` + `bukit-plugin-v1`，legacy Labs Protocol source、sample plugin、protocol echo fixture 已删除。

Bukit 1.0 Core 的目标是：

稳定、干净、严格、可测试、可长期维护。

Labs 的目标是：

承载实验能力、迁移工具、AI/自动化工具、调试工具、未来功能孵化。

依赖方向必须是：

Labs  -> Core
Core -X-> Labs

Core 不允许因为 Labs 增加：

配置字段
兼容 fallback
隐藏命令
实验 runtime
特殊路径
迁移逻辑

3. 新功能进入 Labs 的强制规则
3.1 新增功能默认进入 Labs

从现在开始，任何新功能默认不得直接进入：

src/Bukit.Cli
src/Bukit.Engine
src/Bukit.Config
src/Bukit.Content
src/Bukit.Rendering
src/Bukit.Routing
src/Bukit.Shared

必须先进入：

experimental/Bukit.Labs.Cli
experimental/Bukit.Experimental.*
3.2 Labs 验收通过后才可迁移

新功能从 Labs 迁移到 Core 或正式库，必须满足以下条件：

1. 有明确的 1.0/1.x 产品定位。
2. 不依赖实验配置字段。
3. 不需要 Core 增加兼容 fallback。
4. 有完整测试覆盖。
5. 有文档。
6. 有架构审计结论。
7. 有明确迁移 PR 或 ADR。
8. 通过 Labs release gate。

未经以上验收，不得迁移到 Core。

3.3 新功能进入 Core 的流程

必须经过：

Labs implementation
Labs tests
Labs docs
Labs usage validation
Architecture review
Core promotion proposal
Core migration PR
Core release gate

不得直接把新命令加入 BukitCliSpecs.CreateRegistry()。

3.4 必须新增 Architecture Rule

4. P1-2：Deploy provider 契约收紧
4.1 最终 1.0 契约

Bukit 1.0 只支持 GitHub Pages。

标准配置必须明确：

deploy:
  provider: github-pages
  branch: gh-pages
  message: bukit deploy
4.2 Validator 必须拒绝其它 provider

当前 DeployConfig 仍包含：

public string? Provider { get; init; }

当前 DeployCommand 实际固定使用：

new GitHubPagesDeployProvider()

因此必须补齐 validator。

4.3 具体规则
情况 A：没有 deploy 节

允许。

解释：

未配置 deploy 时，不影响 build。
情况 B：存在 deploy 节，但没有 provider

建议拒绝。

报错：

deploy.provider is required when deploy section is present. Bukit 1.0 supports only 'github-pages'.
情况 C：provider 为 github-pages

允许。

情况 D：provider 为其它值

拒绝。

报错：

deploy.provider must be 'github-pages' in Bukit 1.0.
4.4 修改位置

优先在配置验证阶段实现：

src/Bukit.Config/ConfigValidator.cs

新增或扩展：

private static void ValidateDeploy(AppConfig config)
{
    if (config.Deploy is null)
    {
        return;
    }

    if (string.IsNullOrWhiteSpace(config.Deploy.Provider))
    {
        throw new ConfigException(
            "deploy.provider is required when deploy section is present. Bukit 1.0 supports only 'github-pages'.",
            DiagnosticCode.ConfigInvalidValue);
    }

    if (!string.Equals(config.Deploy.Provider.Trim(), "github-pages", StringComparison.OrdinalIgnoreCase))
    {
        throw new ConfigException(
            "deploy.provider must be 'github-pages' in Bukit 1.0.",
            DiagnosticCode.ConfigInvalidValue);
    }
}

并确保主 Validate(AppConfig config) 调用它。

4.5 DeployCommand 二次防线

在 DeployCommand.RunAsync 中，在创建 provider 前增加：

var providerName = deployConfig.Provider ?? "github-pages";

if (!string.Equals(providerName, "github-pages", StringComparison.OrdinalIgnoreCase))
{
    Console.Error.WriteLine("deploy.provider must be 'github-pages' in Bukit 1.0.");
    return 2;
}

如果选择“deploy 节存在时 provider 必填”，这个检查仍保留作为 CLI 侧防线。

4.6 文档和示例更新

所有涉及 deploy 的示例必须写：

  provider: github-pages
  branch: gh-pages
  message: bukit deploy

不得继续使用隐式 provider。
