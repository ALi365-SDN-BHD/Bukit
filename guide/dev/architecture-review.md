# 项目架构评审意见稿

本文档从维护者视角，对当前仓库架构做一次偏正式的评审，目标不是重复介绍模块划分，而是回答三个问题：

- 当前架构是否总体合理
- 哪些设计值得保留
- 哪些地方存在局限、风险与后续演进空间

## 1. 评审结论

当前仓库的整体架构是**优秀且成熟的工程化架构**，尤其在以下方面表现突出：

- 分层清晰
- 单向依赖明确
- 扩展点设计合理
- 文档与测试配套较完整
- Bukit 与 AIBuilding 的产品边界处理得较稳健

但这套架构也存在几个重要局限，它们并不意味着“设计混乱”，而是说明该项目在追求 **AOT、轻依赖、明确边界和可交付性** 的同时，牺牲了一部分：

- 超大规模站点的内存效率
- 更彻底的通用化能力
- 更现代的 CLI 交互体验
- 更开放的动态插件生态

## 2. 评审范围

本次评审覆盖以下主线：

- Bukit 主体：CLI、Config、Content、Routing、Rendering、Engine、Plugins
- AIBuilding：桌面端 AI 工具、与 Bukit 的桥接方式
- 构建模式：普通 .NET 模式与 Native AOT 模式

本次评审不聚焦具体业务功能正确性，而聚焦：

- 结构合理性
- 可维护性
- 可扩展性
- 可测试性
- 规模化上限

## 3. 主要优点

### 3.1 模块职责边界清楚

当前主链条非常清晰：

```text
CLI -> Config -> Content -> Routing -> Rendering -> Engine -> Plugins -> Output
```

各层的职责划分也较克制：

- CLI 负责命令与参数入口
- Config 负责配置契约、默认值和校验
- Content 负责把不同来源统一为 `ContentItem`
- Routing 负责路由决策
- Rendering 负责模板渲染
- Engine 负责编排与 IO
- Plugins 负责扩展行为

这种边界设计非常有利于维护和定位问题。

### 3.2 单向依赖设计合理

当前项目没有明显出现“底层反向依赖上层”的架构腐化迹象，整体依赖方向较健康：

- CLI 依赖 Engine / Config
- Engine 依赖 Content / Routing / Rendering
- Plugins 通过 Abstractions 契约访问系统
- AIBuilding 通过文件与 CLI 协议连接 Bukit，而不是直接耦合内部引擎实现

这使得系统在长期演进时具备更好的稳定性。

### 3.3 插件体系抽象正确

插件体系将扩展点分成两类：

- `derive-pages`
- `after-build`

这个划分非常贴合静态站点生成器的领域模型：

- 前者适合生成额外页面
- 后者适合生成 sitemap/rss/search/taxonomy 等聚合产物

这比“只有一个宽泛的插件钩子”要更容易治理。

### 3.4 AIBuilding 与 Bukit 的边界处理得稳

AIBuilding 没有强行变成 Bukit 的程序集级上层依赖，而是采用：

- 项目目录
- `site.yaml`
- 外部 `bukit` CLI 进程

作为桥接协议。

这意味着：

- Bukit 可以继续作为独立 CLI 产品演进
- AIBuilding 可以作为上层工作流工具存在
- 两者之间的耦合集中在“文件协议和构建约定”上，而不是类库实现细节上

这是一种很稳健的产品线解耦方式。

## 4. 主要不足与局限

## 4.1 内存模型偏重

### 现状

当前引擎会在较早阶段全量加载内容集合，并把完整正文 HTML 一并保存在内存结构中。

### 问题

这会带来两个直接后果：

- 站点规模扩大时，内存消耗随内容体量线性上升
- 正文 HTML 在很多阶段并不真正需要，却提前进入内存

对于几百篇内容的小中型站点，这个问题通常不明显；但如果进入数万篇内容规模，风险会明显放大。

### 风险等级

- **高**

### 影响范围

- 大站点构建
- CI 环境内存敏感场景
- 多语言构建时的峰值内存

### 评审意见

当前问题的本质不是“全量集合一定错误”，而是：

> **全量集合里不应该默认包含完整正文 HTML。**

像 taxonomy、分页、搜索索引、归档、多语言过滤这类能力，仍然需要全量元数据视图；但正文内容应更倾向于：

- 延迟加载
- 按需读取
- 缓存文件引用

### 建议方向

- 保留全量元数据集合
- 将正文从 `ContentItem` 中拆成“可延迟获取的正文引用”
- 在渲染阶段按需回读正文
- 配合现有增量构建 manifest，减少重复读取与重复渲染

## 4.2 路由模型仍偏约定优先

### 现状

当前系统已经支持 `permalinks`，但默认路由仍然保留对 `post` 与 `page` 的内置约定。

### 问题

这说明项目已经开始向“可配置路由”演进，但尚未彻底完成“通用集合驱动”的抽象。

结果是：

- 对博客类站点很友好
- 对更复杂内容类型或多 collection 场景支持仍不够彻底

### 风险等级

- **中高**

### 影响范围

- 更通用的 CMS 化场景
- 多内容类型项目
- 后续新增内容类型时的扩展一致性

### 评审意见

当前路由设计不是错误，而是典型的“从约定型产品向通用平台演进到一半”的状态。

### 建议方向

- 引入 `collections` 级配置
- 让 collection 定义自己的：
  - 类型
  - 路由模式
  - 模板
  - 列表页策略
- 将 `post/page` 默认规则降级为兼容层，而不是长期保留为内置硬编码核心

## 4.3 CLI 层扩展性有限

### 现状

当前 CLI 参数解析较轻量，依赖较少，适合当前命令规模和 AOT 目标。

### 问题

这种实现虽然简单可控，但上限较低：

- 参数 schema 不够声明式
- Help 与错误提示能力有限
- 参数校验逻辑容易散落在命令实现内部
- 随命令增长，维护成本会逐步提高

### 风险等级

- **中**

### 影响范围

- CLI 体验
- 新命令扩展
- 用户自解释能力

### 评审意见

这一点不应简单定性为“重复造轮子”，因为轻量实现本身与 AOT 目标是相容的。

更准确的评价应该是：

> **它是一个保守、可控、轻依赖的工程取舍，但牺牲了 CLI 的现代化体验与长期扩展性。**

### 建议方向

有两种可选路线：

- 路线 A：继续保留轻量解析器，但补齐声明式参数定义、统一错误提示和自动 help 生成
- 路线 B：评估更成熟 CLI 框架，但必须先确认其对 AOT、裁剪与包体的影响

不建议在未评估 AOT 成本前，直接替换为更重的命令行框架。

## 4.4 AOT 模式限制了动态插件生态

### 现状

当前插件生态分为两种模式：

- 非 AOT：支持外部程序集插件
- AOT：只能使用内置插件和编译期生成插件

### 问题

这意味着 AOT 交付模式虽然更适合部署和性能，但会显著收缩插件扩展能力。

对于希望发展第三方生态的项目来说，这是一个重要上限。

### 风险等级

- **中高**

### 影响范围

- 开源插件生态
- 第三方扩展接入门槛
- 分发模式的一致性

### 评审意见

这并不是“实现有 bug”，而是 Native AOT 的真实边界。

因此，问题不在于“为什么没支持动态 DLL”，而在于：

> **项目是否已经为长期生态化准备了替代性的插件宿主模型。**

当前答案是：还没有。

### 建议方向

建议按成本分阶段推进：

- 短期：明确双模式定位  
  - AOT 追求交付性能与稳定性  
  - 非 AOT 追求外部插件扩展
- 中期：设计进程外插件协议  
  - 使用 JSON / stdin-stdout / 文件交换作为稳定边界
- 长期：若生态目标明确，再评估 WASM 或脚本宿主

直接引入 WASM、Lua、Jint 并不是错误方向，但对当前项目阶段来说偏重。

## 5. 额外值得关注的结构性问题

除了上面 4 个重点外，还有几个值得持续观察的问题。

### 5.1 内容侧复杂度可能继续集中

Notion 相关能力天然复杂，随着字段解析、块渲染、relation、cache、限流、taxonomy 等能力增长，内容层有继续膨胀为“复杂中心”的风险。

建议长期保持以下拆分原则：

- 属性解析器独立
- 块渲染器独立
- 远程 API 适配层独立
- 缓存与限流策略独立

### 5.2 文件协议需要更显式的契约治理

AIBuilding 与 Bukit 的解耦方式本身是合理的，但“文件协议”如果没有契约测试，就容易在后续演进中出现隐性不兼容。

建议为以下内容增加契约测试：

- AIBuilding 生成的 `site.yaml`
- 默认主题目录结构
- 构建输出目录关键产物

### 5.3 发布路径需要更权威的一致性

当前仓库已经有多条 CI / build / pages 相关工作流，但维护者需要更容易判断：

- 哪条是当前正式发布路径
- 哪条是模板
- 哪条是实验性或备用流程

这属于“交付治理问题”，不是核心代码问题，但会直接影响维护体验。

## 6. 综合评分

按维护者视角给出一份主观但尽量克制的评分：

| 维度 | 评分 | 说明 |
|---|---|---|
| 可维护性 | 8.5 / 10 | 分层与边界很清晰，文档配套完整 |
| 可扩展性 | 8.0 / 10 | 插件与模块抽象合理，但通用性仍有上限 |
| 可测试性 | 7.0 / 10 | 核心链路覆盖不错，但全局状态和外部依赖仍影响隔离性 |
| 可交付性 | 8.0 / 10 | AOT、示例、smoke、文档都比较成熟 |
| 规模化潜力 | 6.5 / 10 | 当前最大限制来自正文全量入内存 |
| 开放生态潜力 | 6.5 / 10 | AOT 对动态插件生态形成天然收缩 |

## 7. 优先级建议

如果只做 3 件最值得做的事，建议按下面顺序推进：

### 优先级 1：重构内容内存模型

目标：

- 元数据全量
- 正文延迟

收益：

- 直接提升大站点承载能力
- 为后续增量和缓存优化打基础

### 优先级 2：引入 collection 驱动的路由抽象

目标：

- 从 `post/page` 约定型模型演进到通用集合模型

收益：

- 提升通用性
- 降低未来内容类型扩展成本

### 优先级 3：明确插件生态双模式路线

目标：

- 清晰区分 AOT 与非 AOT 插件能力
- 设计中期的进程外插件协议

收益：

- 降低生态路线的不确定性
- 为长期开放扩展能力留出稳定边界

## 8. 最终判断

这不是一个“架构有问题”的项目。

更准确地说，这是一个：

- 在工程组织上已经相当成熟
- 在产品边界上处理得比较克制
- 在交付能力上明显优先于纯理论通用性
- 但在超大规模内存效率、完全通用化路由、CLI 现代体验和开放生态方面还有演进空间

如果把结论压缩成一句话：

> **当前架构已经是一个优秀的、可维护的静态站点生成器架构；它的主要局限不在“乱”，而在“为了稳定交付和 AOT 选择了更保守的能力边界”。**
