# Bukit 架构与性能审计计划

## Summary

* 目标：基于仓库当前实现，评估项目在架构设计与性能治理上的成熟度，形成一份可执行的审计报告与优化路线图。

* 审计范围：`src/` 下核心构建链路，重点覆盖 `Cli -> Config -> Content -> Routing -> Rendering -> Engine -> Plugins`，并结合 `tests/`、`guide/dev/`、`scripts/` 判断治理成熟度。

* 输出形式：以“审计报告”为主，不做架构重写假设；重点给出“当前水平判断 + 主要风险 + 分优先级优化项 + 验证方式”。

* 总体判断：当前项目属于“中上水平、工程化较完整、可扩展性较好、性能治理已起步但在大规模内容场景仍有明显热点”的静态站点引擎。

## Current State Analysis

### 1. 架构成熟度判断

* 分层结构清晰，主链路稳定：

  * CLI 入口：`src/Bukit.Cli/Program.cs`

  * 配置解析：`src/Bukit.Config/ConfigLoader.cs`

  * 内容加载：`src/Bukit.Content/Markdown/MarkdownFolderProvider.cs`、`src/Bukit.Content/Notion/NotionContentProvider.cs`

  * 路由生成：`src/Bukit.Routing/RouteGenerator.cs`

  * 模板渲染：`src/Bukit.Rendering/Scriban/ScribanTemplateRenderer.cs`

  * 构建编排：`src/Bukit.Engine/SiteEngine.cs`

  * 插件扩展：`src/Bukit.Engine/Plugins/*`

* 项目自带架构文档，且文档与代码基本一致：`guide/dev/architecture.md` 明确说明 `SiteEngine` 已从超大 God Class 拆成薄编排器 + 专职组件，这说明维护者有明确的边界治理意识。

* 关键组件具备接口抽象，说明可测试性与未来可替换性较好：

  * `ITemplateRenderer`

  * `IContentProviderFactory`

  * `ISearchIndexBuilder`

* 插件系统具备内置插件、协议插件、外部程序集插件三层扩展能力，说明架构不是“仅够用”，而是已经考虑了扩展生态。

* 测试面覆盖 CLI / Content / Engine / Rendering 四层，说明基础工程质量高于一般个人工具仓库。

### 2. 工程治理成熟度判断

* 全局质量门较完整：

  * `Directory.Build.props` 开启 `TreatWarningsAsErrors=true`

  * 开启 `EnforceCodeStyleInBuild=true`

  * 使用最新分析级别

* AOT 治理是显式能力而不是附带产物：

  * `src/Bukit.Cli/Bukit.Cli.csproj` 开启 `PublishAot=true`

  * `guide/dev/perf-aot-governance.md`

  * `scripts/check-aot-warnings.sh`

  * `scripts/perf-baseline.sh`

* 仓库有 smoke、性能基线、AOT 告警治理文档，说明团队已经具备“度量与回归控制”意识。

* 综合看，这个项目的工程治理成熟度高于普通开源 side project，接近“有明确维护策略的小型产品型项目”。

### 3. 当前架构优势

* `SiteEngine` 目前控制在薄编排器形态，主职责是 orchestration，不再承担全部细节实现。

* Content / Routing / Rendering / Engine 职责边界基本合理，单向依赖关系健康。

* Notion 与 Markdown 共用统一 `ContentItem` 模型，内容层抽象有效。

* 增量构建、i18n、多站点、搜索、sitemap、taxonomy、分页都围绕统一构建上下文工作，整体一致性较强。

* 模板能力探测、搜索索引、指标输出、协议插件等说明项目已经从“功能实现”进入“平台型能力抽象”阶段。

### 4. 当前架构问题与风险

* 编排层虽然已大幅改善，但 `src/Bukit.Engine/SiteEngine.cs` 仍然承担过多流程拼装责任：

  * 内容加载

  * i18n 变体循环

  * 资产同步

  * manifest 管理

  * 渲染调度

  * 插件调度

  * metrics 输出

* `PageRenderDispatcher` 已不只是“渲染器调度”，还承担：

  * 增量跳过判断

  * 列表页定义构建

  * 列表页内容装配

  * 文件写入协同
    这使它正在演化为新的高复杂度组件。

* Notion 内容提供器承担了较多职责：

  * 数据库分页抓取

  * Property 解析

  * relation 补全

  * taxonomy 提升

  * 页面 HTML 缓存

  * auto summary
    这类“胖 Provider”后续继续增长时，会降低可维护性。

* 当前缺少更明确的“性能预算对象”或“热点分层指标”，性能观测仍偏结果型，而不是路径级诊断型。

### 5. 当前性能能力判断

* 已具备的性能能力：

  * 页面渲染并行：`src/Bukit.Engine/PageRenderDispatcher.cs`

  * 增量构建 manifest：`src/Bukit.Engine/Incremental/*`

  * 模板解析缓存：`src/Bukit.Rendering/Scriban/ScribanTemplateRenderer.cs`

  * include 文件缓存：`src/Bukit.Rendering/Scriban/FileTemplateLoader.cs`

  * Notion HTML 缓存：`src/Bukit.Content/Notion/NotionContentProvider.cs`

  * Notion Body single-flight：`src/Bukit.Content/Notion/NotionBodyStore.cs`

  * 图片下载缓存与单飞：`src/Bukit.Content/Media/ImageAssetLocalizer.cs`

* 说明项目性能水平不是“未优化”，而是已经完成第一阶段优化，具备基本的并发、缓存、增量与度量闭环。

* 但现阶段优化重心主要落在“缓存与跳过”，对“大规模数据集下的算法复杂度”和“远程内容源请求拓扑”优化还不够深入。

### 6. 主要性能热点

#### P0: 大列表与全量物化

* `src/Bukit.Engine/PageRenderDispatcher.cs`

  * `renderQueue = routed.Concat(pluginContext.DerivedRouted).ToList()`

  * 首页、集合列表、legacy list 都会 `Where/OrderByDescending/ToList`

  * `BuildPageInfosAsync` 对列表逐项构建 `PageInfo`

* 风险：

  * 站点内容规模上升后，CPU 花在排序、切片、复制、对象分配上的比例会明显提升。

  * 内存峰值会因多个列表页同时持有完整 `PageInfo` 集合而变高。

#### P0: 增量判定成本过高

* `src/Bukit.Engine/Incremental/IncrementalBuildEngine.cs`

  * `ComputeContentHash()` 直接读取正文 HTML

  * `ComputeListContentHash()` 在缺 manifest 命中时会回退到逐项计算内容 hash

* 风险：

  * 理论上“跳过渲染”应是便宜路径，但现在某些情况下为了判断是否跳过，已经先做了昂贵正文读取。

  * 当正文来自 Notion 渲染缓存、图片重写或大 HTML 内容时，skip 判定不够轻。

#### P0: Notion 请求拓扑可能退化为 N 次远程调用

* `src/Bukit.Content/Notion/NotionContentProvider.cs`

  * 数据库 query 分页抓取

  * taxonomy relation 缺失目标时逐个 `GET /pages/{id}`

  * 页面正文渲染时递归抓取 block children

* 风险：

  * 大数据库、复杂 relation、深层 block 结构会导致请求数线性放大。

  * 这类瓶颈通常不是 CPU，而是远程 API RTT、限流等待、串行依赖。

#### P1: 列表页渲染仍存在串行尾部

* `src/Bukit.Engine/PageRenderDispatcher.cs`

  * `RenderSpecialListsAsync()` 中特殊列表页按 `foreach` 顺序执行

* 风险：

  * 主页面已并行，而特殊列表仍是串行，导致整体构建尾延迟明显。

#### P1: 图片重写是高频多轮正则扫描

* `src/Bukit.Content/Media/ContentImageRewritePipeline.cs`

  * 对同一段 HTML 做 6 次 pass

  * 每次 pass 中逐个 `await _localizer.LocalizeAsync(...)`

* 风险：

  * 长文、多图、富媒体页面下会形成 CPU 与 async 往返热点。

#### P1: 模板目录 hash 与媒体复制在大项目下有固定成本

* `src/Bukit.Engine/Incremental/HashUtil.cs`

  * 每次构建遍历并读取 layouts 目录内容生成 `templateHash`

* `src/Bukit.Engine/SiteEngine.cs`

  * 媒体文件逐个 `File.Copy`

* 风险：

  * 这些操作不是最重热点，但会在大站点下形成稳定的前后置耗时。

## Proposed Changes

### 第一阶段：先补强“观测与定位”，再做定点优化

* 在 `src/Bukit.Engine/PageRenderDispatcher.cs`、`src/Bukit.Content/Notion/NotionContentProvider.cs`、`src/Bukit.Content/Media/ContentImageRewritePipeline.cs` 增加更细粒度 metrics：

  * 列表页构建耗时

  * 正文 hash 计算耗时

  * Notion relation resolve 请求数

  * block 渲染耗时与请求数

  * 图片重写耗时与命中率

* 原因：

  * 当前已有 `metrics.json` 能力，但还不足以把瓶颈拆到函数责任层。

* 预期结果：

  * 后续优化不再依赖主观判断，而能按真实热点排序。

### 第二阶段：压低增量判定成本

* 目标文件：

  * `src/Bukit.Engine/Incremental/IncrementalBuildEngine.cs`

  * `src/Bukit.Engine/PageRenderDispatcher.cs`

  * `src/Bukit.Engine/Incremental/BuildManifest.cs`

* 调整方向：

  * 将正文 hash 与轻量元数据 hash 分层，优先用轻量 fingerprint 做 skip 判定。

  * 对列表页内容 hash 尽量基于已存在的 item/route 指纹组合，而不是临时再读取全文。

  * 为列表页、正文页引入更稳定的“内容版本指纹”字段，减少运行时重复读取。

* 为什么优先做：

  * 这是当前“增量构建看似存在，但低收益时仍可能很重”的根因。

### 第三阶段：重构大列表处理策略

* 目标文件：

  * `src/Bukit.Engine/PageRenderDispatcher.cs`

  * `src/Bukit.Engine/Plugins/BuiltIn/PaginationPlugin.cs`

  * `src/Bukit.Engine/Plugins/BuiltIn/ArchivePlugin.cs`

  * `src/Bukit.Engine/Plugins/BuiltIn/TaxonomyPlugin.cs`

* 调整方向：

  * 减少重复 `Where/OrderBy/ToList`，将通用排序结果复用化。

  * 将“列表定义构建”与“列表内容装配”拆开，降低 `PageRenderDispatcher` 复杂度。

  * 在 `includeContent=false` 情况下，确保只传递轻量 `PageInfo` 数据，不触发正文加载。

  * 为分页、taxonomy、archive 建立共享的排序/筛选中间索引。

* 为什么优先级高：

  * 这类优化既提升性能，也改善组件职责边界，是架构与性能双收益点。

### 第四阶段：优化 Notion 远程请求拓扑

* 目标文件：

  * `src/Bukit.Content/Notion/NotionContentProvider.cs`

  * `src/Bukit.Content/Notion/NotionBlocksRenderer.cs`

  * `src/Bukit.Engine/Plugins/BuiltIn/PagesIndexPlugin.cs`

* 调整方向：

  * 收敛 relation resolve 的触发条件，优先利用已有 page index。

  * 明确区分“构建页正文必须请求”和“仅为 metadata 补全而请求”的路径。

  * 为 block children、table rows 建立更可控的缓存与请求统计。

  * 检查能否将部分 relation 解析延后到真正需要的插件或模板路径。

* 原因：

  * 远程内容源的性能瓶颈通常比本地算法更影响真实用户构建体验。

### 第五阶段：处理渲染尾部与媒体扫描热点

* 目标文件：

  * `src/Bukit.Engine/PageRenderDispatcher.cs`

  * `src/Bukit.Content/Media/ContentImageRewritePipeline.cs`

* 调整方向：

  * 将特殊列表页渲染纳入有限并行。

  * 评估将多轮 regex pass 合并为更少轮次，或先做 cheap precheck 再决定是否进入重写流程。

  * 对同一 HTML 中重复 URL 的本地化结果做局部缓存，减少重复 await。

* 原因：

  * 这类优化改动面相对可控，收益通常比较稳定。

### 第六阶段：继续做架构降复杂度

* 目标文件：

  * `src/Bukit.Engine/SiteEngine.cs`

  * `src/Bukit.Engine/PageRenderDispatcher.cs`

  * `src/Bukit.Content/Notion/NotionContentProvider.cs`

* 调整方向：

  * 继续把 `SiteEngine` 中的变体构建、资产同步、manifest 生命周期管理下沉为独立服务。

  * 将 `PageRenderDispatcher` 拆为：

    * Render planner

    * Incremental evaluator

    * List page assembler

    * Output writer

  * 将 `NotionContentProvider` 拆为：

    * Database loader

    * Relation resolver

    * Page HTML cache service

    * Summary extractor

* 原因：

  * 这是控制未来复杂度增长、避免出现“第二个 God Class”的关键步骤。

## Assumptions & Decisions

* 本次判断基于仓库当前本地代码，不包含线上真实站点规模、生产 metrics、真实 Notion 数据量。

* “项目水平”定义为：分层设计、扩展能力、测试治理、构建治理、性能治理、可维护性六项综合判断，而非只看代码行数或框架新旧。

* 输出重点是“核心架构 + 性能”，不展开 UI、SEO 模板语义、业务功能正确性审计。

* 结论采用保守判断：

  * 架构层面：中上，已具备产品化雏形。

  * 工程治理：较强。

  * 性能治理：有明确意识，但在大规模内容与远程源场景仍未到“成熟优化完成”阶段。

## Verification Steps

* 代码级核验：

  * 对照 `guide/dev/architecture.md` 与 `src/` 实现，确认文档与当前模块边界一致。

  * 逐个核查 `SiteEngine`、`PageRenderDispatcher`、`IncrementalBuildEngine`、`NotionContentProvider`、`ContentImageRewritePipeline` 的职责与热点。

* 工程级核验：

  * 对照 `Directory.Build.props`、`src/Bukit.Cli/Bukit.Cli.csproj`、`scripts/perf-baseline.sh`、`guide/dev/perf-aot-governance.md` 判断治理成熟度。

* 风险级别核验：

  * 以“影响面 + 触发概率 + 改造收益”给性能问题排序，优先确认 P0/P1 项。

* 后续执行建议：

  * 若进入执行阶段，先做 metrics 细化，再做增量 hash 与列表路径优化，不建议直接进行大规模架构重写。
