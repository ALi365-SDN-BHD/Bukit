# Changelog

All notable changes to Bukit will be documented in this file.

## [Unreleased]

## [2.2.0] - 2026-11-14

- **An interrupted snapshot commit keeps the last good snapshot**: if a recording build is killed between the two directory renames, the old snapshot stays next to the target and an offline open explains that a backup exists. The next successful recording creates or replaces the target, and a later recording removes the backup.
- **Notion offline snapshots are checked by format version only**: the snapshot still records `bukitVersion` for diagnosis, but upgrading Bukit no longer invalidates it; only a change to `NotionSnapshotSession.FormatVersion` requires recording again. A recording build reuses the rendered bodies of an older snapshot, and bodies from another `NotionBlocksRenderer.ContractVersion` are rendered again.
- **Notion and snapshot failures carry stable `BKT-0Bxx` codes**: Notion API 401/403/404/429/other HTTP/network/invalid JSON, a missing mapped property, and every offline snapshot failure now have a stable code. `build` writes it to the cli-error JSON; `config check` and `doctor` print `[BKT-0Bxx]`; a multilingual worker passes its code and reason to the parent. Top-level config, content and render errors now use the documented `BKT-xxxx` form instead of the enum name. A single-language build that fails on a snapshot exits 2; a multilingual worker failure keeps exit 1. The public `DiagnosticCode` enum gains 16 Notion members (0B01–0B08 and 0B10–0B17); the public API baseline is updated.

## [2.1.0] - 2026-11-14

- **Breaking: `site.languages` is the only language setting**: `site.language` is no longer accepted in `site.yaml` and fails with `site.language was removed; write languages: [<code>] instead, for example languages: [en].` Write `languages: [en]` instead of `language: en`. When `site.languages` is missing or empty it means `[zh-CN]`; a list whose entries are all blank is an error, and a `defaultLanguage` that is not in `site.languages` now fails with `site.defaultLanguage must be included in site.languages.` instead of logging `i18n.config.default_language_ignored`. Templates still read the current language as `{{ site.language }}`. `bukit labs init`, Labs intents and the HTML demo importer now write `languages`; an intent with `site.language` is rejected and should use `languages.supported: [<code>]`, where `languages.default` may be omitted for one language. Code that uses the Labs assembly directly must also change: `SiteIntentSite.Language` is removed and `SiteIntentLanguages.Default` is now optional.
- **Breaking: one entry in `site.languages` builds a single-language site**: `languages: [en]` now builds at the output root, like a site without a language list, instead of a one-language variant under `dist/en/`. `defaultLanguage`, when set, must equal that entry. Move host redirects or links that pointed at `/<lang>/` for such a site. For such a site `content/en/` and `data/en/` are now ordinary folders, not a language directory and overlay: same-named files under `content/en/` keep `en/` in their fallback slugs (for example `en/a/foo`), `data/en/` is read under the nested key `en`, and page IDs must be unique across the whole site. A site that moves from `language: en` to `languages: [en]` keeps its incremental cache.
- **Breaking: `site.defaultLanguageInSubdir` defaults to `false`**: a multilingual site that does not set it now builds the default language at the output root (`dist/`, site root base URL) while other languages keep `dist/<lang>/`, so adding a second language keeps the default-language URLs. Add `defaultLanguageInSubdir: true` to keep every language under `/<lang>/`. The first build after the layout changes runs the protected clean of the output directory, which needs `dist/.bukit-output-marker`. The setting now changes the incremental hash only when it is `true` on a site with two or more languages, and `i18n.config.default_language_layout_ignored` is logged for a single-language site only when it is `true`. With the default setting, adding a second language to a single-language site also counts as a layout change and runs that clean once, and the default-language URLs stay the same; with `true` the layout does not change, no clean runs, and the default language moves under `/<lang>/`.
- **The merged audit no longer reports a false manifest mismatch with a root default language**: with the default language at the root and merged sitemap or search, the merged agent manifest lists `/index/` for the default language next to `/zh-CN/index/`, and the publish audit compared the `zh-CN` page with the default-language entry, logging `publish.manifest_mismatch`. A route that matches only after adding the language prefix must now also have the same language.
- **Pages without a language use the site language on a single-language site**: such pages now carry the site language instead of `und` in `agent-manifest.json`, the per-page `.json` and `.md` projections and JSON Feed items, matching `search.json`, and the publish audit expects the same. Multilingual sites keep `und` there.
- **The publish audit prefers an exact agent-manifest route**: an entry that matched a page only after adding its first output segment (for example `/foo/` for `/posts/foo/`) could be picked before the page's own entry and log a false `publish.manifest_mismatch`.
- **Redirect pages no longer render again after every content edit**: alias pages and the root-layout legacy home redirect were recorded as reading every shared collection, so editing any page rendered them again. They now read none; their target still decides when they change.
- **Removed languages no longer leave `dist/<lang>/` behind**: when a multilingual site becomes single-language or drops a language, the former `dist/<lang>/.bukit` reports are removed with the stale pages, so the empty `dist/<lang>/` disappears.
- **No false `geo.llms_txt_missing` with a root default language**: the default language's own audit warned that `llms.txt` and `llms-full.txt` were missing, although the root writes them after every language.
- **Single-language search records use the site language**: `search.json` records without a page language now carry the site language instead of `und`; `und` remains only when no language is known.
- **`metrics.json` records the effective languages**: when `site.languages` is not set in `site.yaml`, `site.languages` is now `["zh-CN"]` instead of `null` (a config built in code without `Languages` records `[site.language]`), and `site.language` is the site's default language (the only language of a single-language site).
- **Merged audit language fallback**: in a multilingual build whose default language is prefixed, a route the merged audit cannot assign to a language now falls back to the default language.
- **Tokens can be passed on standard input with `--secrets-stdin`**: `build`, `dev`, `doctor`, `config check`, and `deploy` take a new `--secrets-stdin` flag. Bukit then reads standard input to end of file before any other work and expects one JSON object of at most 64 KiB that maps names to non-empty strings, such as `{"NOTION_TOKEN":"…","GITHUB_TOKEN":"…"}`. Each token Bukit needs (`NOTION_TOKEN`, and for `deploy` the name given by `--token-env`, default `GITHUB_TOKEN`) is taken from that object first, then from the environment. On macOS and Linux other programs of the same user can read a running process's environment, so callers such as a desktop app no longer have to put tokens there. Stdin values are never copied into an environment, so `git`, Sass, image tools, and plugins started by Bukit do not inherit them; multilingual build workers receive them on their own stdin; log lines, top-level errors, and plugin reports replace them with `***`. Unusable input (empty, invalid JSON or UTF-8, a non-string or empty value, an invalid or duplicate name, more than 64 KiB, stdin attached to a terminal, or a command that does not take the flag) fails with exit code 2 and error code `secrets-stdin-invalid`, and the message never repeats the input. Without the flag nothing changes, and existing error messages are unchanged. Known limit: `deploy` still hands the GitHub token to each authenticated `git` process in that process's environment (`BUKIT_GITHUB_TOKEN`, read by a temporary `GIT_ASKPASS` script), where other programs of the same user can read it while `git` runs.
- **Notion offline snapshot**: `build --notion-snapshot <dir>` with `NOTION_TOKEN` records the raw Notion API data of the build (database schema, every queried page with all properties and Notion's server time, relation targets, the cross-source relation fallback, taxonomy select options, `pages_index` pages) and the rendered bodies. `build`, `config check` and `doctor` with `--notion-snapshot <dir> --notion-offline` then need no token, create no Notion client and make no request. Anything the snapshot lacks is an error instead of a silent skip; a `databaseId` it does not hold fails, a changed filter or sort builds from the recorded pages with an `event=notion.snapshot.query_changed` warning, and `propertyMap` or template changes work. Images come only from the existing media cache. The snapshot is replaced only after a successful build, is private (`0700`/`0600`), never contains the token, and carries its format and Bukit version. `--notion-snapshot` overrides `cacheMode` and `cacheDir`, so nothing is cached in the site directory. See the Notion guide.
- **Page count per content source**: every build logs `event=content.source.loaded source=<name> count=<n>` for each source.
- **Multilingual builds resolve `pages_index` Notion relations in every language**: each language worker read list fields such as relation ids back from the shared content as plain object lists, so `theme.params.pages_index.resolve_notion` silently resolved nothing in multilingual builds (and an offline build silently skipped relation targets missing from the Notion snapshot). Lists of strings now keep their type, so workers resolve relations like a single-language build and a missing snapshot entry fails the build.
- **The merged publish audit matches each route to its own translation**: in a multilingual build, translations that share an ID were matched to a content record by the first route segment, falling back to `site.language`, which a multilingual build does not use. Under a `baseUrl` such as `/docs` that segment was `docs`, and with the default language at the root its routes have no language segment, so these routes could take another language's record: the merged `publish-audit-report.json` and `.bukit/seo-route-map.json` then showed that language, summary, author and dates, the representation and trust checks in `seo-report.json` compared against it, and the feed window check used its publish date. The base path is now removed before reading the language segment, and routes without one use the language written at the output root. Built pages are unchanged.
- **A failed image download no longer fails the build when the placeholder file is missing**: with the default `content.media.onFailure: placeholder`, an image that could not be downloaded was replaced by `content.media.defaultImageUrl` (default `/assets/images/noneimg-news.jpg`), and when neither the theme nor the site had that file the build stopped with `Referenced localized media output is missing`. Bukit now checks the theme's and site's `static/` and `assets/` directories (including a parent theme) before localizing images. If the placeholder is missing, a failed image keeps its original URL, as `onFailure: keep` does, and each such image logs `event=media.placeholder_missing` once per page with the image URL (scheme, host and path; userinfo, query and fragment left out), the page, the placeholder and the two fixes. When the placeholder exists it is used as before, and the default of `onFailure` is unchanged. `bukit doctor` and `bukit config check` warn when `onFailure: placeholder` points at a missing file. When a page still links to a missing placeholder (for example a template that references it directly), the error keeps its first line `Referenced localized media output is missing: <path>`, now followed by a space, the pages that link to it and the fixes. Tools that read everything after the colon must now read only up to the first whitespace.
- **Behavior change: `site.language` must be a safe language code** (later removed; see the `site.languages` entry above): without `site.languages`, `site.language` now has to use letters and digits in hyphen-separated subtags (such as `en`, `zh-CN` or `zh-Hant-TW`), the rule `site.languages` already follows. A value such as `en_US` or one containing a quote, `/` or `<` now fails validation with `site.language must use safe alphanumeric subtags separated by hyphens.` instead of being written into `<html lang>`. Use `en-US` instead of `en_US`. A blank value is still accepted, and `site.language` is not checked when `site.languages` is set. The HTML demo importer now writes a safe language: it turns a page `lang` such as `zh_CN` into `zh-CN`, falls back to `zh` when the page value is still unsafe, and rejects an unsafe `--language` instead of writing a `site.yaml` that cannot build.
- **Starter theme search shows only the current language**: the starter theme search page (`layouts/pages/search.html`, written by theme scaffolding and clone) fetches `{{ site.base_url }}/search.json`, which with the default language at the root and `search.mode: merged` is the merged index, so default-language search results mixed every language. The page now keeps records whose `language` matches `site.language` (case-insensitively) or is `und`. Existing themes are not rewritten; copy the filter into a scaffolded `search.html` to pick it up.
- **Every search record names its language**: list and taxonomy records whose pages carry no language used to omit `language` in `search.json`, and pages without a language were recorded as `und` even inside a language of a multilingual site. Every record now has `language`: records without their own language take the language of the variant that wrote them in a multilingual site, otherwise `und`. Clients can filter the merged index by `language` without special cases.
- **Behavior change: the search UI loads its own language's index**: `bukit-search.html` fetched the hard-coded `/search.json`, so it found nothing on a site served under a `baseUrl` such as `/repo/`, and in a multilingual site every language searched the root file (missing in `split` and `index` modes, the merged index in `merged` mode). The fragment now reads the index URL from the input's `data-search-url` attribute, set to `<language base URL>/search.json` (for example `/repo/zh-CN/search.json`; with the default language at the root and `search.mode: merged`, `/<defaultLanguage>/search.json`); `/search.json` remains the fallback when the attribute is removed. In `search.mode: merged` the fragment now searches only its own language; to search another index, copy the fragment markup into a template and set `data-search-url` there (the generated file is rewritten on every build). When the index fails to load or is not an array, the fragment shows "Search is unavailable" instead of empty results, and a query typed while the index was loading runs once it arrives.
- **Optional redirects for every old default-language URL**: `site.defaultLanguageLegacyRedirects` (default `false`) helps sites that move a live default language to the root layout on hosts without 301s, such as GitHub Pages. With `defaultLanguageInSubdir: false` it writes a noindex meta-refresh page at the old `/<defaultLanguage>/...` path of every default-language HTML page (content, collection lists and pagination, taxonomy pages, static HTML routes, and aliases, which point straight at their page). The home page stays controlled by `defaultLanguageRedirect`, existing outputs at those paths win, and non-HTML files and taxonomy aliases are not redirected. The build logs one `i18n.legacy_redirects.derived` summary; route counts and reports grow by the number of redirects. With the prefixed layout the option is ignored and logs `i18n.config.legacy_redirects_ignored`. Alias redirect documents now also record their target page; their HTML is unchanged. Sites that leave the option off see no output change.
- **The default language can live at the output root**: `site.defaultLanguageInSubdir` (default `true` at the time; now `false`, see above) keeps every language under `dist/<lang>/`; setting it to `false` builds the default language into `dist/` with the site root base URL while other languages keep `dist/<lang>/`. `site.defaultLanguageRedirect` (default `true`) writes a noindex home redirect page so `/` works on static hosting: `dist/index.html` → `/<defaultLanguage>/` in the prefixed layout, or `dist/<defaultLanguage>/index.html` → `/` in the root layout. The page is excluded from sitemaps, search, feeds, llms and the agent manifest. **Behavior change**: an existing multilingual site gains `dist/index.html` after upgrading; a site whose host or CDN already redirects `/` to `/<language>/` should set `defaultLanguageRedirect: false`. With the root layout, per-language reports move to `.bukit/variants/<lang>/`, `search.mode: merged` keeps the merged index at `/search.json` and writes the default language's own index to `/<defaultLanguage>/search.json`, the default language may not use another language code as its first path segment (`i18n-route-reserved-language-prefix`), a default-language `static/robots.txt` overrides generated robots, and other static files colliding with root-owned outputs fail with `i18n-root-output-conflict`.
- **Behavior change: merged sitemap and feed modes no longer write per-language copies**: with `site.languages` set, `sitemapMode: merged` used to leave a `dist/<lang>/sitemap.xml` in every language, written by the per-language publish projection although the documented contract is a single root sitemap; `feed.mode: merged` likewise left per-language `rss.xml`, `<feed.path>/atom.xml`, `<feed.path>/feed.json` and collection feeds. These per-language files are no longer generated in either layout, and language `publish-audit` reports mark those representations as not generated. Submit the root `sitemap.xml` to search engines, and point feed links, including theme links built from `{{ site.base_url }}/rss.xml`, at the root merged feeds.
- **Single-language sites own their merged-mode sitemap and feeds**: without `site.languages`, `sitemapMode: merged` and `feed.mode: merged` already wrote `sitemap.xml` and the feeds, but the build manifest did not record them. They are now owned outputs: turning the feature off later removes the stale files, and a same-named `static/` file fails with `BuildAssetOutputCollision` exactly as in split mode.
- **Behavior change: redirect pages are noindex everywhere**: alias pages and the root-layout legacy home redirect (`/<defaultLanguage>/`) are now generated with `robots: noindex` and excluded from sitemaps, search and feeds. On every site that uses `aliases`, these pages no longer appear in `llms.txt` and publish audits no longer treat them as indexable pages (no more `publish.sitemap_missing_route` or `publish.search_missing_route` warnings for them).
- **Static checks follow `build.followSymlinks`**: the root-output conflict check and the legacy home redirect now treat a symlink in `static/` exactly as the copy step does: ignored when `followSymlinks` is off, and counted only when it resolves inside the static directory when it is on. A symlink that the copy step skips no longer fails the build or suppresses the redirect. The theme token stylesheet (`assets/css/theme-tokens.css`) is also checked against reserved language prefixes, so a language code `assets` with the default language at the root fails with `i18n-route-reserved-language-prefix`.
- **Only an exact `static/robots.txt` replaces the generated robots**: with the default language at the root, a static file named `Robots.txt` (or any other casing) now fails with `i18n-root-output-conflict` instead of suppressing the generated `robots.txt`; crawlers request only the lowercase path, so on case-sensitive hosts the site was left without robots rules. The root output conflict check now also skips dot-prefixed paths the copy step skips (unless `build.publishDotFiles` is on), and the default language audit follows the same dotfile and symlink rules when deciding whether a static `robots.txt` exists.
- **Redirect pages are complete raw HTML**: alias pages now bypass the HTML transform pipeline, so SEO title/analytics injection no longer modifies them; they are written as the complete redirect document. Alias and taxonomy redirect pages also gain `<title>` and `<meta name="robots" content="noindex">`. On the default prefixed layout, alias output therefore changes; the redirect target and location are unchanged.
- **Translations that share a slug no longer fail strict schema validation**: `canonical_duplicate_id` now checks ids within one language when `site.languages` is set; a page without a language counts as the default language, and single-language sites still require site-wide unique ids. Translations that use the same file name or slug in each language (for example `content/en/index.md` and `content/zh/index.md`) share an id by design, but each pair logged a duplicate-id warning and failed the build under `build.schemaFailMode: strict`. `bukit doctor` no longer reports these pairs as a blocking schema error either. Two pages with the same id in one language still report the warning, now naming the language.
- **Multi-language builds log each audit issue once**: `seo.audit`, `publish.audit` and `geo.audit` issues were logged twice, once by each language variant with a route that had no language prefix (so `/index/` appeared once per language) and again by the merged audit with the full route. Variants now only write their report files. The parent logs the merged audit's issues together with each language's own issues (with the language prefix added to the route, for checks that only run per language such as a per-language sitemap in `split` mode), and logs each distinct issue once with routes such as `/en/index/`. The build report warning and error counts no longer count these issues twice, so they drop for multi-language sites. Per-language `.bukit/seo-report.json` files are unchanged. If the build fails while writing root outputs, the languages' own issues and the signed-link warning are still logged before the error.
- **Multi-language builds log the signed-link warning once**: `event=incremental.signed_links` was logged once per language, usually with the same keys because languages read the same shared data. Languages now hand their findings to the parent, which logs one line for languages with identical findings, with a comma-separated list such as `language=en,zh-CN`. Languages with different findings still get their own line. Log parsers should expect a comma list in `language=`, and the build report warning count drops by one for each repeated line. Single-language builds are unchanged.
- **i18n diagnostics for dropped and duplicated content**: builds now log `i18n.document.language_unknown` when a page's `language` is not in `site.languages` (or is not `site.language` in a single-language build), `i18n.document.i18n_key_duplicate` when two pages in one language share an `i18nKey`, and `i18n.config.default_language_ignored` when `site.defaultLanguage` is set without `site.languages` (that warning was later removed; see the `site.languages` entries above). These pages or configurations were previously ignored or overwritten without a warning. A single-language site that intentionally selects one language from a mixed-language source now warns about the other languages on every build; warnings are capped at five per kind plus one summary line, and the build report warning count can rise. Apart from the `i18n_key` public ID change below, output for valid sites is unchanged.
- **Doctor checks every configured language**: `bukit doctor` now builds and validates routes for every `site.languages` entry instead of only the default language, so a route conflict or missing template that exists only in a non-default language fails doctor instead of waiting for the build.
- **`i18n_key` now drives public IDs**: pages that use the `i18n_key` alias now use that value for `id` and `canonicalId` in `agent-manifest.json` and public content projections, matching `i18nKey`. Previously the alias fell back to the slug, so the same translation group could have different public IDs in different languages. Sites that use `i18nKey` or a slug fallback are unchanged.
- **llms curation diagnostics now run**: invalid page-level `geo.llms` curation (an unknown key, a bad `visibility` or `tier`, a `priority` that is not an integer such as `"10"` or is outside -100 to 100, `llms: false`, or a non-empty `geo:` value that is not a mapping) now logs `geo.llms_field_unknown`, `geo.llms_visibility_invalid`, `geo.llms_tier_invalid`, `geo.llms_priority_invalid` or `geo.llms_shape_invalid` (a `geo` or `llms` value that is not a mapping), each with `route=<output path>`, during the build for every routed page (including noindex pages), and fails the build under `site.seo.diagnostics: strict`. Since the publish projection refactor these checks never ran, so such pages were dropped from `llms.txt` and `llms-full.txt` without a warning. Sites that use `strict` and have invalid curation will now fail to build; fix the front matter or use `visibility: exclude`. Valid curation and output are unchanged. An empty (or whitespace-only) `geo:` or `llms:` key is now treated as absent: such a page is included in `llms.txt` and `llms-full.txt` and no longer fails a `strict` build (before, it was excluded silently).

## [2.0.15] - 2026-11-11

- **Expired image links fail fast**: when an image download is refused (HTTP 400, 401 or 403) and the URL's own signature has expired (AWS SigV4, Google Cloud Storage V4, AWS SigV2/CloudFront, or the Notion file proxy), it is no longer retried `content.media.maxRetries` times, since an expired signature can never succeed. This mostly speeds up builds from a `readonly` Notion cache that still holds expired links. The failure, `onFailure` result and reuse of already saved images are unchanged, and the warning gains `signature=expired`. Other failures keep their retries.
- **Warning for signed links in shared data**: with incremental builds, Bukit now logs one `event=incremental.signed_links` warning when `site.modules`, `site.data`, `site.data_index`, `site.related_pages`, `site.data_files`, the route metadata source or page fields (key `pages`) still hold links of a recognized signing scheme (AWS SigV4, Google Cloud Storage V4, AWS SigV2/CloudFront, Notion file proxy). It names each read key and its link count, plus `language=` in multi-language builds. These links may change on every fetch, so the pages that read them may render again on every build; localize the files with `content.media` to avoid that. Hashing and output are unchanged.
- **`bodyFingerprint` is no longer shown for other pages**: in the `pages` list and in section `source` items, `fields` no longer holds the internal `bodyFingerprint` value. It identifies the body, which those lists do not track, so a page that printed it could keep stale text after another page's body edit. A page's own `page.fields` is unchanged.
- **Plugin name and option case no longer re-render the site**: plugin names and top-level option names are matched ignoring case, and the incremental hash now treats them the same way, so changing only their case no longer renders every page again.

## [2.0.14] - 2026-11-10

- **Notion bodies follow renderer changes and same-minute edits**: the Notion body cache (format 2) records the renderer version and the fetch time from Notion's `Date` header. In `readwrite` mode a cached body is reused only for the same renderer version and `last_edited_time`, with unexpired links, and only if it was fetched at least 5 seconds after the edit minute ended, so an edit made later in the same minute as a fetch is no longer lost. The incremental body fingerprint becomes `{last_edited_time}:renderer={version}[:unsettled]:content={on|off}`; pages without `last_edited_time` get their content hash from the body. The first `readwrite` build after upgrading fetches every Notion body again, which can take a long time on large databases. `readonly` still reuses matching entries and reports older ones in one `notion.cache.renderer_mismatch` warning; build with `--clean` when switching back to `readwrite`.

## [2.0.13] - 2026-11-10

- **Faster rendering on large sites**: each page used to convert the whole site page index (`pages`) and the site model (`site`, including `site.data.pages_by_id`) again, so render time grew with the square of the page count. They are now converted once per render pass and shared. Output is unchanged for templates that only read them. Behavior change: `site`, `pages`, list-page `items` and everything inside them are now read-only at every level, so a template that adds a new key to them or assigns an array element (such as `pages[0] = x`) fails with a read-only error; inside components and sections the error follows `theme.componentValidation`.
- **Render and report timing**: `--metrics` now records real `pageRender`, `listBuild` and `staticRender` times (they were always 0), plus `renderCall`, `htmlTransform`, `renderWrite`, `renderModelBind` and `renderDispatch`, and the pre-render variant steps `variantSetup`, `mediaResolve`, `renderPlan`, `assetPrepare` and `seoPrepare`. Each report step after rendering logs `event=build.report.timing` with its duration, and each scope ends with `step=total`. Report files and the `metrics.json` structure are unchanged.
- **Faster report stage on large sites**: checking whether each route appears in `sitemap.xml`, `search.json`, `agent-manifest.json`, `llms.txt` and the other aggregate files now scans each file once instead of once per route; the publish audit reads and parses `agent-manifest.json` once instead of once per document; and media output validation computes the effective media settings once instead of once per link. On a 4,651-page site these three steps took most of the build. Output, report files and audit issues are unchanged.
- **Re-signed images keep their file**: a localized image's file name no longer changes when only its signature changes. For URLs signed with AWS SigV4, Google Cloud Storage V4, AWS SigV2/CloudFront (`Signature` with `AWSAccessKeyId`, `GoogleAccessId` or `Key-Pair-Id`), or served by the Notion file proxy (`notion.so`, `*.notion.so`, `*.notion.site`), the signature and expiry parameters are left out of the file's identity; all other parameters still count, and the download still uses the full signed URL. Notion images are therefore downloaded once instead of again on every build after their links expire. When one link to an image has expired but another reference has a fresh signature, the fresh one is used. After upgrading, signed images are downloaded once more under their new stable name, except that a file an earlier version stored is still used for the exact signed URL it came from, so a `readonly` Notion cache with expired links keeps its local images; unsigned images keep their file names.
- **Incremental builds notice engine and plugin changes**: the template hash now includes the Bukit engine version and source revision, so the first `--no-clean` build after upgrading renders every page again (reported as `template_changed`, lists as `list_render`) instead of keeping pages rendered by the old engine. Options of enabled built-in plugins now count as render inputs, so changing one renders the site again; key order does not matter. Builds without git metadata or with uncommitted changes share their release's identity and need `--clean`.
- **Render reason `metadata_changed`**: pages re-rendered because their record or custom fields changed are now counted as `metadata_changed` in `renderReasons` of `.bukit/incremental-manifest.json`; `content_changed` now means the body alone changed, including a changed `bodyFingerprint` (for example a Markdown body edit). Editing a Notion page also updates its `last_edited_time` field, so Notion edits show as `metadata_changed`. Scripts that read `content_changed` should also read `metadata_changed`.
- **Editing one page no longer re-renders the whole site**: `--no-clean` builds now track shared data per page. Bukit records which collections each page's templates (layout, includes, components and sections) read: a `site.data`, `site.modules` or `site.data_index` key, `site.related_pages`, `site.data_files`, or `pages` (also read by sections with a `source`). Editing an article re-renders that article and the pages that read data it changed, such as `site.data.pages_by_id`, lists and pages that loop over `pages`, reported as the new render reason `data_dependency_changed`; site-wide setting changes are still `render_dependency_changed`. A template that uses `site` or `site.data` as a whole, an unknown global, `this` or a section plugin counts as reading everything, as does a custom renderer. Pages that loop over `pages` now also re-render when another page changes, where they used to keep stale HTML. `build-manifest.json` gains the optional entry fields `renderReads` and `renderBaseHash`; the first `--no-clean` build after upgrading renders every page.

- **Content Signals in robots.txt**: `site.seo.robotsTxt.contentSignal` (`search`, `aiInput`, `aiTrain`, each `true` or `false`) writes a `Content-Signal:` line in the `User-agent: *` group, for example `Content-Signal: search=yes, ai-input=yes, ai-train=no`, so a site can say how AI companies may use its content. Only set values are listed. Unset, `robots.txt` is unchanged.
