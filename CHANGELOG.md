# Changelog

All notable changes to Bukit will be documented in this file.

## [Unreleased]

- **CloudBase content source**: `content.sources[].type: cloudbase` reads a CloudBase PG-mode table or view through PostgREST, projects fields with hard-excluded personal columns, renders Markdown with the untrusted-link policy, signs `fileFields` objects and body `cloud://` images, and falls back to `content.media.defaultImageUrl` on file-resolution failures. The build privacy check rejects envId, `cloud://`, gateway/storage hosts and signed links; the deploy check rejects token-bearing signed links, `cloud://` in URL positions, and envId when configured. `doctor` checks the credential role, table reachability, RLS-empty results and storage signing. See [27 CloudBase Content](guide/user/27-cloudbase-content.md).

- **Responsive variants for WebP images**: with `theme.images.enabled`, local static WebP images (for example covers and body images downloaded from Notion or WeChat) now get resized WebP candidates at the configured widths below their own width, and their `img` gets a `srcset`, as JPEG/PNG images already did. They are not wrapped in `<picture>`. Animated WebP, files whose name already ends in `-<width>w.webp`, and WebP files beside a JPEG/PNG of the same name are left as uploaded. WebP sources are always resized with SkiaSharp. Sites with WebP media gain the variant files and their freshness sidecars, the affected `img` tags gain `srcset` and `decoding="async"`, and the first incremental build after upgrading re-renders pages because the image fingerprint now includes WebP files. See [04 site.yaml Config](guide/user/04-site-yaml-config.md).

- **RSS channel language and absolute item URLs**: `rss.xml` and collection RSS feeds now write `<language>` when every item shares one declared language (blank and `und` are ignored, so a mixed-language merged feed has none), and root-relative `src`, `href` and `srcset` URLs inside `content:encoded` become absolute against `site.url`. In the merged i18n root feed, items without a language take their variant's language.

- **Valid Open Graph locales**: `og:locale` is now a valid Open Graph locale. A language with a region passes through (`zh-CN` → `zh_CN`), common bare codes get a default region (`en` → `en_US`, `pt` → `pt_BR`), and an unknown bare code omits the tag. Pages also emit `og:locale:alternate` for their hreflang alternates. A `site.language` with no Open Graph locale warns `seo.og_locale_region_missing` (a warning even with `strict`). See [SEO](docs/seo.md).

- **No hreflang on noindex pages**: a noindex page no longer emits hreflang alternates (nor `og:locale:alternate`), and indexable pages, the sitemap's `xhtml:link` entries and `page.seo.alternates` no longer list noindex translations or empty `noindexWhenEmpty` list pages.

- **Breadcrumb taxonomy parent after URL ancestors**: with `site.seo.schema.breadcrumbParent`, BreadcrumbList now reads Home › URL ancestors › term page › page instead of putting the term page before the URL ancestors; a term page that is itself a URL ancestor appears once. See [11 I18n And SEO](guide/user/11-i18n-seo.md).

- **JSON-LD language and dates**: `WebSite` JSON-LD names `site.language` in `inLanguage`, and `WebPage`/`CollectionPage` names the page language. `datePublished`, `dateModified` and `dateReviewed` are written at second precision in `site.timezone` (`2026-06-05T18:00:00+08:00`) instead of the round-trip format, as are the `article:published_time` and `article:modified_time` meta tags and the `page.seo.article.published_time`/`modified_time` template values, and sitemap `<lastmod>` is the date in `site.timezone`. The publish audit's `publish.jsonld_date_mismatch` compares a JSON-LD date-time with the publish time on the calendar of its own offset, so the same instant no longer warns.

- **Percent-encoded sitemap URLs**: sitemap `<loc>` and `xhtml:link` `href` values percent-encode, as UTF-8 per RFC 3986, non-ASCII and other non-URI characters after the host (`/新闻/` → `/%E6%96%B0%E9%97%BB/`). HTML canonical and hreflang tags are unchanged. The publish audit still finds noindex pages with non-ASCII URLs in the sitemap.

- **Image dimensions and lazy loading**: with `theme.images.enabled`, a media image whose size Bukit reads gets `width` and `height` from its displayed size (after EXIF orientation) when it has neither, and every media image on a page but the first gets `loading="lazy"` when it has no `loading` attribute, so the first (often the largest above-the-fold image) still loads immediately; author-written values are never changed. Incremental builds re-render pages when a media image's height changes, and the first incremental build after upgrading re-renders every page. See [04 site.yaml Config](guide/user/04-site-yaml-config.md).

- **No ImageMagick**: Bukit no longer runs ImageMagick (`magick` or `convert`) for responsive image resizing or AVIF asset conversion, even when it is installed; AVIF is skipped as before (`image_avif.skip`) without a converter run, and resizing always uses the built-in SkiaSharp encoder, so no external image tool is needed. Resized variants made by ImageMagick are regenerated once on the next build. See [04 site.yaml Config](guide/user/04-site-yaml-config.md).

- **Search page without BOM**: `bukit-search.html` is written as UTF-8 without a byte order mark.

- **Smaller PNG image variants**: with `theme.images.enabled`, resized variants of PNG sources with no transparent pixels (including RGBA files whose pixels are all opaque) are written as RGB PNG instead of RGBA, so they no longer carry an unused alpha channel; sources with transparency stay RGBA. File names, URLs and HTML are unchanged. Existing variants regenerate once on the next build.

- **Resized variants for media images only**: with `theme.images.enabled`, resized original-format variants (for example `logo-480w.png`) are generated only for media images under `content.media.urlBase`, the only images that get an original-format `srcset`. Theme and static images elsewhere under `assets/` no longer get these unreferenced files; they still get their WebP candidates and `<picture>` when WebP is enabled, and resized variants an earlier build made for them are deleted on the next build. See [04 site.yaml Config](guide/user/04-site-yaml-config.md).

- **Structured Markdown bodies**: the body of each `content/<page>.md` representation and of `llms-full.txt` keeps headings (demoted two levels, `<h1>` as `###` down to `######`, so they stay below the projection's own title and sections), paragraphs, line breaks, nested lists, block quotes, horizontal rules (`* * *`, never the `---` document separator of `llms-full.txt`) and code blocks (fenced, verbatim, with a fence longer than any backtick run in the code) instead of collapsing onto one line. Links stay Markdown links, images are still left out, and script, style, template and comment content is still dropped. `search.json` content is unchanged. The publish audit now reads only the metadata header of a `.md` file (up to `## Entities` or `## Body`), so body list items such as `- Source: ...` no longer raise `publish.representation_markdown_mismatch`.

- **Agent manifest 1.1: real publish dates and list routes**: `agent-manifest.json` now declares `schemaVersion` `1.1`. **`publishedAt` changes meaning**: it now holds the publish date, while the last edit time moves to a new optional `updatedAt` (present only when the record has one); before, `publishedAt` held the edit time whenever there was one. `generatedAt` is still the latest change (the newest `updatedAt`, or `publishedAt` for a record without one). A new optional `lists` array names each home, collection list and taxonomy route the sitemap lists (`route`, `language`, `kind`, `lastModified`, and `representations` with the page URL in the same `{kind, url}` form as documents); `lists` routes use the same route space as `documents` routes in that manifest, and `lists` is empty without `site.url`. The root merged manifest of a multilingual site includes every language's lists. `docs/schemas/agent-manifest.v1.schema.json` keeps its `$id` and accepts `1.0` and `1.1`; `wechat-sync` reads any `1.x` manifest. See [10 Built-In Outputs](guide/user/10-built-in-outputs.md).

- **Collection feeds no longer repeat a single site feed; RSS authors use `dc:creator`**: the new `site.collections.<name>.output.feed` decides whether a collection writes its own feeds; `output.rss` now only puts the collection in the site feed. Left unset, `output.feed` is `true` only when two or more collections have `output.rss: true`. **A site with one RSS collection no longer writes `<feed.path>/<name>/rss.xml`** (or its Atom and JSON twins) beside an identical `/rss.xml`; set `output.feed: true` to keep it. RSS items now write the author as `<dc:creator>` with the Dublin Core namespace instead of `<author>`, which RSS 2.0 reserves for an email address.

- **Dates, author and original source in the Markdown header**: each `content/<page>.md` header now adds `- Published:`, `- Updated:` (when set), `- Author:` and `- Original Source:` after `- Canonical:`, matching the JSON projection. Dates use `site.timezone` in the same format as `article:published_time`; `Original Source` is the public original URL, never the private `source` provenance; line breaks in these values become spaces so they cannot forge another header line.

- **Per-language site identity**: the new `site.i18n.<lang>` map lets a multilingual site set `title`, `description` and `organization` (`name`, `url`, `logo`, `sameAs`) for one language. That language's build uses them for the `<title>` suffix, `og:site_name`, the default description, JSON-LD `WebSite` and `Organization`, its feeds and `llms.txt`, and `site.title` in templates; organization fields merge one by one over `site.seo.organization`. Root merged outputs keep the top-level identity. The language key must be a `site.languages` entry, and the map requires two or more languages.

- **Localized term pages pair across languages**: a taxonomy term can declare `i18nKey` in `content/_taxonomy/<kind>/<slug>/_index.md` front matter or on a `sourceKey: tags|categories` data document. Term pages with the same kind, key and page number now list each other in hreflang and sitemap alternates, so `/tags/马来西亚/` and `/en/tags/malaysia/` pair; without a key they still pair by URL. Two terms of one kind that share a key in one language log `taxonomy.term.i18n_key_duplicate` and fall back to URL pairing.

- **No robots.txt under language directories**: a multilingual build no longer writes `robots.txt` into non-root language directories such as `zh-CN/robots.txt`, because crawlers read it only at the host root, where the root writer already places the site file. Localized `404.html` copies stay and are now documented, and a test confirms that a single-file `site.sharedAssets.paths` entry such as `favicon.ico` is shared.

- **Article schema default and author profiles**: `site.seo.schema.articleType` and `site.collections.<name>.seo.articleType` set the JSON-LD type of article pages that declare none (page, then collection, then site, then `BlogPosting`). `site.seo.authors` maps author names and `authoredBy` ids to a profile (`name`, `type`, `url`, `image`, `sameAs`), so text bylines, GEO and default authors get an author URL, and a Markdown `authoredBy: <id>` no longer blocks the build when the id has an entry.

- **`sizes` for generated srcsets**: `theme.images.sizesAttribute` (unset by default) adds a CSS `sizes` value beside the `srcset` Bukit generates for media images, so browsers stop assuming `100vw` and downloading oversized candidates. Lazy images get `sizes="auto, <value>"`, and the eager first image gets the plain value. Author-written `sizes` are kept, and the value also reaches the WebP `<source>`.

- **og:image dimensions and WebP warning**: when the social image is a file of the site, Bukit writes `og:image:width`, `og:image:height`, and `og:image:type` (also `page.seo.og.image_width`, `image_height`, and `image_type` for themes and the starter theme), so previews render before the image is fetched. WebP share images now warn `seo.og_image_webp`, since some platforms show no preview for WebP.

- **WebP-only image variants**: `theme.images.fallbackVariants: none` (default `all`) skips the resized original-format variants of JPEG/PNG media images when WebP is generated. The `<picture>` keeps its WebP candidates, and the fallback `<img>` keeps only its original `src`, which cuts output size and build time for sites that do not need srcsets for browsers without WebP.

## [2.2.8] - 2026-11-23

- **Object values in the data index**: `content.sources[].dataIndex` rows accept the value types `object` (one mapping) and `object[]` (a list of mappings), so templates can read `site.data_index.<source>.<scope>.<key>.<field>` and `dataIndex` mini-program datasets that declare `object` receive real objects. Markdown rows give the value as YAML; Notion rows give it as JSON text (parsed without reflection, so it works in the Native AOT binary). Booleans and numbers are typed, so `if info.open` is false for `false` and `info.days > 3` compares numbers: Notion JSON keeps its types (a JSON string such as `"5"` stays text), and a Markdown scalar becomes a boolean when it is `true`/`false` (YAML core spellings) and a number when it is written like a JSON number; other text such as `0123`, `+60` or `yes` stays text, and quoting does not keep `"5"` as text in Markdown. Whole numbers within 64 bits are integers and other numbers decimals that keep their digits (`12.50`), so a value builds the same model and incremental hash from either source, and `dataIndex` mini-program datasets write them as JSON booleans and numbers. Keys are ordinal-sorted and must not be blank, nesting is limited to 8 levels (each mapping or list is one), a single mapping given to `object[]` is a list of one (as for mini-program `object[]` fields), and numbers outside the double range, invalid JSON, duplicate keys or the wrong shape fail the build naming the source, content id and `scope.key`. An empty object value is an empty mapping or list; a mapping or list holding only empty values counts as empty for `requiredKeys`. **Behavior changes**: a `text`, `multiline`, `email`, `phone` or `url` row whose value is a YAML mapping or list used to build silently and render the .NET type name (`System.Collections.Generic.Dictionary...`); it now fails the build. Numbers and dates in those text rows are now formatted culture-invariantly instead of with the build machine's culture. See [07 Multi-Source Data](guide/user/07-multi-source-data.md#object-values).

- **Image localization reaches inside front matter objects**: `content.media.fieldKeys` now also applies inside front matter mappings and lists at any depth, by each value's own key, on every page and data record, not only mini-program datasets. A page with `hero: { image: https://cdn.example.com/a.jpg }` or `features: [{ icon: …, image: … }]` now downloads those images during the build (with `content.media.downloadToLocal` on, the default), and templates see the local `/assets/uploads/...` path, or `content.media.defaultImageUrl` when a download fails under `onFailure: placeholder`. Localized links inside objects are copied to the output like top-level ones. Text that is not a URL under a nested `icon` key logs `media.skip_non_http` and is kept. To keep a nested remote link, use a key outside `fieldKeys`. See [04 site.yaml Config](guide/user/04-site-yaml-config.md).

- **Object fields in mini-program datasets**: `miniprogram` dataset `types` now accept `object` and `object[]`, so a route's `days: [{title, text, stay, meals, sights, exps}]` is written to its detail file instead of failing the build. A type can also be a mapping `{ type, fields }` whose `fields` declare nested types the same way, and must declare at least one typed field (an empty `fields` fails config validation instead of writing every object as `{}`; omit `fields` to keep every key); declared fields project each object to exactly those keys, and undeclared objects keep every key with inferred values. Nested `image` and `url` values become absolute http(s) URLs and signed URLs fail; remote images inside objects are downloaded when their own key is listed in `content.media.fieldKeys`, at any depth, and localized media inside objects is copied to the output; nested strings stay plain text (only `body` is HTML), keys are written in ordinal order so hashes depend only on content, `NaN` fails at any depth, and nesting deeper than 8 levels fails with `SchemaValidationFailed` naming the dataset, record and field path. `dataIndex` datasets accept the same types. A catalog that uses an object field is `schemaVersion` and `minClientSchema` `1.1`; sites without one keep `1.0` and byte-identical output. Put object lists in `detailFields` to keep list files small. See [25 Mini-Program Data](guide/user/25-miniprogram-data.md#object-fields).

- **YAML nulls in Markdown front matter are null**: an unquoted `null`, `Null`, `NULL`, `~` or empty value in front matter (content and `mode: data` Markdown sources) used to become the text `"null"`, `"~"` or `""`. It is now a real null at every depth: a top-level key with a null value is treated as absent, and a null inside a mapping or a nested list stays null. Quoted values such as `"null"` and values tagged `!!str` (`!!str null`) are still text. Template impact: Scriban treats any non-empty string as true, so `if page.subtitle` was true for `subtitle: null` and printed `null`; such a field is now absent and the condition is false. A null item in a top-level list of text (`sights: [a, null]`, or an empty `- ` item) is dropped, as an empty item was before, so the field stays a list of text for templates, tags, `string[]` mini-program fields and image localization; a top-level list of only nulls is absent, like a top-level null. A list inside a mapping keeps the null in place; a mini-program `string[]` value drops it, and one of only nulls is empty (written as `null`, rejected by `required`). Sites that wanted the literal text must quote it.

- **Safe JSON output in templates**: `util.json_string` now also escapes `<`, `>`, `&`, U+2028 and U+2029 (as `\u003c`, `\u003e`, `\u0026`, `\u2028`, `\u2029`), so a value containing `</script>` (for example from Notion) can no longer end a theme's `<script type="application/ld+json">` early. The output is still valid JSON with the same decoded value, but its bytes change wherever a value contains one of these characters. The new `util.to_json value` serializes objects, arrays, strings, numbers, booleans, null and dates with the same escaping and ordinal key order (of dictionary keys that become the same text, such as `1` and `"1"`, the first is kept), without reflection, so it works in the Native AOT `bukit` binary. Scriban's `object.to_json`, which failed there with BKT-0399, now uses the same implementation; its object keys are sorted rather than in insertion order. `util.*` functions now also work inside theme components and sections, which previously had no `util` object. See [08 Themes And Templates](guide/user/08-themes-templates.md#json-in-templates).

- **Incremental builds report the same page warnings as full builds**: per-page render warnings such as `seo.theme_json_ld_replaced`, `seo.canonical_missing` and the other per-page HTML checks used to be logged only for pages and lists that rendered again, so an incremental build that skipped them reported fewer warnings than the full build. The build cache manifest (`.cache/build-manifest.json`) now stores each page's and list's warnings as `renderWarnings`, and a build that skips an unchanged page logs them again. A page that renders again replaces its stored warnings, so a fixed warning disappears, and changing `site.seo.diagnostics` now renders every page again so the replayed warnings follow the new setting.

- **Inject mode keeps marked theme JSON-LD and warns before dropping the rest**: with `site.seo.renderMode: inject`, a head `<script type="application/ld+json" data-bukit-seo="keep">` now stays where the theme wrote it, so themes can publish types Core does not generate (`TouristTrip`, `Product`, `Event`, ...). Unmarked head JSON-LD is still replaced by Core's, but when its content differs from every Core block the build now warns `seo.theme_json_ld_replaced route=<url> count=<n>` instead of dropping it silently; repeats across pages collapse into `event=diagnostics.summary`. It stays a warning under `site.seo.diagnostics: strict`, so existing strict builds keep passing. A theme that echoes `page.seo.json_ld` in the head is not warned, even when it is pretty-printed or escaped differently. A kept script whose top-level `@type` one of Core's JSON-LD blocks on that page also declares (two `BreadcrumbList` blocks, say) warns `seo.theme_json_ld_duplicate_type route=<url> types=<types>`, also a warning under `strict` and collapsed the same way. The publish audit validates kept head JSON-LD (`seo.json_ld_invalid`) and adds its types to the route's `schemaTypes`; it now reports `seo.json_ld_type_missing` for every JSON-LD block without an `@type` ("block <n> of <total>", counted separately for Core and kept head JSON-LD), where a block after a typed one used to go unreported. Body JSON-LD and the `theme` and `off` modes are unchanged.

- **Configurable template loop limit**: the new `build.templateLoopLimit` (positive integer, default 1000, Scriban's own default) sets how many loop iterations page, component and section templates may run. Scriban counts every iteration inside one outermost loop, including nested loops and loops in functions or includes it calls, so two nested loops over 40 pages and 30 tags fail at 1200 iterations although neither reaches 1000 alone. The `Render failed` error for this case now explains that and names `build.templateLoopLimit` with its current value; component and section diagnostics carry the same hint. Filtering with array.filter or array.map and an anonymous function does not count toward the limit. Sites that do not set the option build exactly as before. See [08 Themes And Templates](guide/user/08-themes-templates.md#loop-limit).

- **Breadcrumb parent in front matter**: a page can set `parent_url: /malaysia/routes/` (the site path of a generated page, without base URL or language prefix) to make that page its BreadcrumbList parent. The trail becomes the parent's trail followed by the page, followed recursively, so a route at `/routes/klang/` can read Home › 马来西亚 › 路线 › 巴生谷三日游; `parent_url: /` makes the home page the parent. Pages below a rewritten page in the URL follow its trail, so `/malaysia/routes/klang/` under a `/malaysia/routes/` with `parent_url: /` reads Home › 路线 › 巴生谷. A parent that is not a generated page, not a site path, or the page itself warns `seo.breadcrumb_parent_missing`; parents that form a cycle, or whose trail already contains the page, warn `seo.breadcrumb_parent_cycle`; those pages keep the URL-inferred trail. The field is named apart from `site.seo.schema.breadcrumbParent`, which sets a taxonomy kind for all pages. Pages without `parent_url` are unchanged. See [11 I18n And SEO](guide/user/11-i18n-seo.md).

## [2.2.7] - 2026-11-21

- **Versioned data for mini-programs (opt-in)**: a new `miniprogram` section in `site.yaml` declares datasets, and each build writes them as JSON under `mp/` in every language output root: content collections (a list plus one detail file per page), data modules, data index scopes, whole data sources (replacing `data/*.yaml`), taxonomy terms and `site.menus` menus, plus a `site` dataset. Every file is named after the SHA-256 of its bytes and listed in `mp/catalog.json` with its hash, so a mini-program requests only the catalog on launch and downloads only what changed. Only declared fields are written; output is byte-identical across rebuilds and operating systems; bodies are reduced to a WeChat `rich-text` safe HTML subset; image and link URLs are absolute. Missing required fields, wrong types and unlocalized signed image URLs fail the build with `SchemaValidationFailed`; an `https://` site URL is required. Bukit does not create the mini-program project. See [25 Mini-Program Data](guide/user/25-miniprogram-data.md). Sites without the section are unchanged.

- **Search works on pages that block `connect-src`**: every `search.json` now has `search.json.js` beside it (`self.bukitSearchIndex=<the same JSON>;`; the `search.index.json` manifest has none). The `bukit-search.html` fragment and the starter theme's search page still `fetch` the index first and load the script only when that fails, so a sandboxed preview whose Content Security Policy has `connect-src 'none'` can search while normal hosting makes the same single request. The script index follows its `search.json` in build manifest ownership and stale-output removal, and a default-language `static/search.json.js` conflicts with the root merged index (`i18n-root-output-conflict`). The script form is only loaded from the page's own origin, so a custom `data-search-url` on another site is fetched but never executed. Search pages already scaffolded into a theme are not rewritten; copy the whole `<script>` block from a newly generated `themes/starter/layouts/pages/search.html` to add the fallback. The output gains one file per search index of the same size.

- **Multi-document YAML is rejected**: `site.yaml`, `theme.yaml`, `bukit.templates.yaml`, and plugin config/manifests must not contain more than one YAML document. Settings in a second document after a `...` or `---` separator used to be ignored; they now fail instead of being ignored. `bukit new` no longer writes a trailing `...`.

## [2.2.5] - 2026-11-16

- **Starter theme refresh**: the starter theme now has a simpler content-first layout, a dark mode that follows the system setting, and a collapsible menu on narrow screens (links stay visible without JavaScript). Interface text comes from `theme.params.labels.*` with English fallbacks; `bukit new --language zh-CN` (and other Simplified Chinese tags, including `zh-Hans-HK`) writes Chinese labels. Navigation module links that start with `/` and taxonomy index links now include `site.baseUrl`, content titles, summaries and tags are HTML-escaped, and the list card no longer shows `country` or `industry`. Existing sites keep their own theme copy; if you copy the new templates into a sub-path site whose navigation links already include the base path, remove that prefix from the links.

## [2.2.4] - 2026-11-16

- **`bukit new` creates a buildable starter site**: `bukit new <dir> [--title <text>] [--language <tag>]` writes `site.yaml`, Markdown content, and the embedded starter theme without running git, a build, or a network request. The generated site passes `config check`, `doctor`, and `build`.

## [2.2.3] - 2026-11-15

- **Deploy uses a local credential broker**: a token read from `--secrets-stdin` is handed to git's credential helper over a private local endpoint and is not placed in the git child's environment or command line. A token read from the environment remains in Bukit's environment and is inherited by git children, as before.
- **The Windows Native AOT binary is reproducible and no longer embeds build paths**: two clean `win-x64` packages now produce an identical `bukit.exe`. The packaging path map did not match Windows paths, so the build machine's temporary build directory was compiled into every assembly, and the linker stamped the link time; packaging now maps native paths and links with `/Brepro`. Release packaging on Linux, macOS and Windows now proves the packaged files against two more clean builds before upload.
- **Offline builds can pin the reviewed Notion field and filter keys**: `build`, `config check` and `doctor` take `--notion-pin <file>` with `--notion-offline`. The file (`{"format":1,"sources":{"<source key>":{…}}}`) checks each source's `databaseId` and replaces `renderContent`, `fieldPolicy`, `propertyMap`, the filter, sort and `includeSlugs` keys and `maxItems` of every Notion source, so an unreviewed `site.yaml` cannot show hidden fields or drafts kept in the snapshot. A key the file omits takes Bukit's default. A Notion source missing from the file fails with `BKT-0B19`, a malformed file with `BKT-0B18`; changed keys are reported as `event=notion.offline.pinned`. The public `DiagnosticCode` enum gains `NotionPinInvalid` and `NotionPinSourceMissing`; the public API baseline is updated.
- **The macOS Native AOT binary is reproducible**: two clean `osx-arm64` packages now produce an identical `bukit`. Apple's linker assigned one `objc_msgSend` stub slot nondeterministically, so the release binary's checksum could change between builds of the same commit; packaging now links with `-objc_stubs_small`. The binary keeps its `LC_UUID`.

- **Shared asset path entries are validated consistently**: `site.sharedAssets.paths` now rejects a leading `\` or a drive-letter prefix on every platform instead of accepting them on POSIX, fails on blank entries instead of dropping them, and normalizes `./fonts/` to `fonts/` so it can match. A leading `/` remains an absolute path and is rejected.

## [2.2.2] - 2026-11-15

- **SEO image URLs keep one base prefix**: localized `record.Media` and custom image fields no longer repeat the language base in `og:image` or Twitter image URLs. This covers non-default languages and sites under a subpath such as `/repo`; shared placeholder URLs under the root base are also recognized.
- **An empty default shared asset set is rejected**: `site.sharedAssets.enabled: true` with no `paths` now fails validation when `content.media.urlBase` covers every default prefix (`assets/` or the enabled SCSS output), instead of silently sharing nothing. Single-language sites keep the documented ignore warning.
- **The dev server watches the root `data/` directory**: `bukit dev` now rebuilds when files under the site's root `data/` change, matching the Worktree input list.

On a 4,651-page site these three steps took most of the build. Output, report files and audit issues are unchanged.
- **Re-signed images keep their file**: a localized image's file name no longer changes when only its signature changes. For URLs signed with AWS SigV4, Google Cloud Storage V4, AWS SigV2/CloudFront (`Signature` with `AWSAccessKeyId`, `GoogleAccessId` or `Key-Pair-Id`), or served by the Notion file proxy (`notion.so`, `*.notion.so`, `*.notion.site`), the signature and expiry parameters are left out of the file's identity; all other parameters still count, and the download still uses the full signed URL. Notion images are therefore downloaded once instead of again on every build after their links expire. When one link to an image has expired but another reference has a fresh signature, the fresh one is used. After upgrading, signed images are downloaded once more under their new stable name, except that a file an earlier version stored is still used for the exact signed URL it came from, so a `readonly` Notion cache with expired links keeps its local images; unsigned images keep their file names.
- **Incremental builds notice engine and plugin changes**: the template hash now includes the Bukit engine version and source revision, so the first `--no-clean` build after upgrading renders every page again (reported as `template_changed`, lists as `list_render`) instead of keeping pages rendered by the old engine. Options of enabled built-in plugins now count as render inputs, so changing one renders the site again; key order does not matter. Builds without git metadata or with uncommitted changes share their release's identity and need `--clean`.
- **Render reason `metadata_changed`**: pages re-rendered because their record or custom fields changed are now counted as `metadata_changed` in `renderReasons` of `.bukit/incremental-manifest.json`; `content_changed` now means the body alone changed, including a changed `bodyFingerprint` (for example a Markdown body edit). Editing a Notion page also updates its `last_edited_time` field, so Notion edits show as `metadata_changed`. Scripts that read `content_changed` should also read `metadata_changed`.
- **Editing one page no longer re-renders the whole site**: `--no-clean` builds now track shared data per page. Bukit records which collections each page's templates (layout, includes, components and sections) read: a `site.data`, `site.modules` or `site.data_index` key, `site.related_pages`, `site.data_files`, or `pages` (also read by sections with a `source`). Editing an article re-renders that article and the pages that read data it changed, such as `site.data.pages_by_id`, lists and pages that loop over `pages`, reported as the new render reason `data_dependency_changed`; site-wide setting changes are still `render_dependency_changed`. A template that uses `site` or `site.data` as a whole, an unknown global, `this` or a section plugin counts as reading everything, as does a custom renderer. Pages that loop over `pages` now also re-render when another page changes, where they used to keep stale HTML. `build-manifest.json` gains the optional entry fields `renderReads` and `renderBaseHash`; the first `--no-clean` build after upgrading renders every page.

- **Content Signals in robots.txt**: `site.seo.robotsTxt.contentSignal` (`search`, `aiInput`, `aiTrain`, each `true` or `false`) writes a `Content-Signal:` line in the `User-agent: *` group, for example `Content-Signal: search=yes, ai-input=yes, ai-train=no`, so a site can say how AI companies may use its content. Only set values are listed. Unset, `robots.txt` is unchanged.
